# Mandible Interface Contract

Version: 14

This section is Mandible's interface contract. It describes daemon and CLI behavior that is the same for every install. It deliberately excludes user policy such as signing key names, branch naming schemes, editor preferences, and worktree tooling.

## Commands

- `mandible changes --project <ref> [--cursor <cursor>] [--limit <1-200>] [--schema mandible-ledger-change-feed@1] [--json]` - Read the bounded project-scoped ledger change feed. Omit --cursor only to establish a controlled resync point, then persist and reuse next_cursor. Retention gaps, truncation, schema mismatch, and inconsistent cursors fail closed.
- `mandible issue report <id> [--json]` - Print deterministic issue context for handoff and planning.
- `mandible issue title <id> [--json] [--graceful]` - Resolve an issue title for caller-supplied commit-message defaults. --graceful makes daemon-unreachable failures non-fatal.
- `mandible umbrella status <id> [--deep] [--json]` - Print one deterministic coordinator fact packet: umbrella body/revision/head, latest delegation manifest, child summaries, parent-role holder state, and repo auth queue summary. Every head object carries both its own digest and an additive subtree_digest covering all transitive parent_child descendants. Child summaries include kind and child_count (direct parent_child children) so nested sub-umbrellas are visible without drilling in. --deep includes child bodies, latest closeouts/comments, branch/auth links, and issue state for parent resumption.
- `mandible umbrella adopt <umbrella> <children...> [--json]` - Idempotently adopt explicit children into an umbrella, create missing parent_child edges, refresh the delegation-manifest checkpoint server-side, and return the updated umbrella status fact packet. This command and `mandible issue link --type parent_child` are the only ways to establish umbrella membership.
- `mandible umbrella manifest refresh <umbrella> [--json]` - Refresh the umbrella delegation-manifest checkpoint from current linked child issue heads server-side without changing parent_child edges, and return the updated umbrella status fact packet.
- `mandible issue parent-role status|assume <umbrella> [--session <id>] [--mechanism <name>] [--override] [--json]` - Inspect or record advisory parent-role holder state. --session accepts a registered Mandible session id or a registered provider session/thread id; the daemon resolves the alias to its canonical session, stores both identities, and rejects an unknown or unregistered id with an actionable error. Liveness comes from the canonical session-liveness rule: a live holder conflict requires an explicit override while a stale holder is informational.
- `mandible issue heads <id>... [--json]` - Print issue state digests for delegation manifests and resume checks. Each head carries its own digest plus an additive subtree_digest over the issue and all transitive parent_child descendants (cycle-safe, each descendant once), so drift two or more levels down a nested umbrella is detectable.
- `mandible issue changed --since-manifest <file> [--json]` - Compare current issue digests with a legacy saved delegation manifest file. Classifies each entry as changed (own digest drifted), subtree_changed (own stable, subtree digest drifted), unchanged, or unknown (manifest predates subtree digests, so subtree drift is indeterminate).
- `mandible issue changed --since-issue <umbrella> [--kind delegation-manifest] [--checkpoint <id>] [--json]` - Compare current issue digests and the umbrella's own head with a structured checkpoint on an umbrella issue; omit --checkpoint to use the latest checkpoint. Classifies each entry as changed, subtree_changed, unchanged, or unknown; unknown means the manifest entry has no baseline subtree digest and never silently reports unchanged.
- `mandible issue checkpoint add <issue-ref> --kind <kind> [--payload <json-or-> | --payload-file <file-or->]` - Append kind-tagged structured issue state outside the comment stream. Use --payload - or --payload-file - to read JSON from stdin.
- `mandible issue checkpoint show <issue-ref> --kind <kind> [--latest|--all] [--json]` - Read kind-tagged structured issue state without parsing comments.
- `mandible issue status <id> <none|in_progress|done|blocked|pivot-needed>` - Set worker coordination status without changing open/closed lifecycle status.
- `mandible issue branch add <id> <branch> [--role primary|superseded]` - Link a branch to an issue as structured coordination state.
- `mandible issue link <src> <target...> [--type t] [--note n]` - Create deliberate structured issue/comment relationship edges with shared action grouping for multi-target links. Accepted types: parent_child, blocks, duplicate_of, related, references, fixed_by, caused_by, implements, tests.
- `mandible issue unlink <src> <target...> [--type t]` - Tombstone deliberate structured issue/comment relationship edges and emit relationship removal events. Accepted types: parent_child, blocks, duplicate_of, related, references, fixed_by, caused_by, implements, tests.
- `mandible issue close <id> --resolution delivered|duplicate|wontfix [--commit <sha>]` - Close an issue with one explicit resolution. The optional --commit link is accepted only for delivered; reopening clears the resolution.
- `mandible issue comment add <issue-ref> -m <text> [--reopen]` - Append rendered Markdown comments with real newline characters and return the issue lifecycle status; --reopen atomically reopens and comments.
- `mandible issue comment edit <comment-ref> -m <body> [--base-revision <rev>] [--base-body-hash <hash>]` - Edit a comment body with optional stale-base checks; comment-ref accepts a raw comment id, <issue-ref>#<ordinal>, or <issue-ref>#last. Conflicts with a stale base return exit code 3.
- `mandible issue description edit <issue-ref> -m <text>` - Edit issue descriptions while preserving body revision history.
- `mandible issue new -t <title> -m <body> --kind bug|feature|umbrella|maintenance|experiment|tracker [--label <label>]...` - Create an issue with one required concrete canonical kind. New issues cannot omit the kind or use unknown; labels remain independent metadata.
- `mandible issue work-notes show|edit|clear|history <issue-ref> [opts]` - Read, replace, clear, or inspect immutable history for the issue's current working notes. Edits and clears use the issue PATCH API with an optional expected working-notes revision.
- `mandible issue kind set <issue-ref> <bug|feature|umbrella|maintenance|experiment|tracker|unknown>` - Set the canonical issue kind through the existing issue PATCH API; kind is independent from labels.
- `mandible issue label add|rm <id> <label>` - Add or remove one free-form label; labels never mirror or mutate canonical issue metadata.
- `mandible auth list [--repo <repo>] [--head <branch>] [--base <branch>] [--status <status>] [--json]` - Find existing auth requests before submitting duplicates.
- `mandible auth check [--branch <branch>] [--repo <repo>] [--target <branch>] [--json]` - Report whether a merge is clean against the target and queued pairwise-independent requests.
- `mandible auth clearance create|list|show|revoke|execute` - Manage immutable operator-issued protected-merge clearances. Prospective creation requires an exact durable agent, canonical project, protected base, issue and/or head, expiry, and bounded use count; a selected request is optional provenance and prefill. Execution requires the requester's exact verified credential provenance.
- `mandible auth request <branch> --title <text> --issue <id> [--closes-issue <id>] [--supersedes <request> --expected-revision <n> --expected-custody-generation <n>] [--drop-superseded-action <ordinal>:<reason>] [--promote-briefing <group> <expected-base> <proposal>] [--message <text> | --message-file <file>] [--verification <text>] [--spec <text>] [--no-watch]` - Submit protected-branch auth work. Each merge request binds atomically to exactly one committed issue-linked delivery work unit owned by the authenticated durable credential. Use --issue for reference context and --closes-issue only for intended closure. --supersedes atomically replaces the exact pending request on the same work unit, project, head, and protected target, guarded by lifecycle revision and custody generation; every staged predecessor action is terminally carried or explicitly dropped with a reason. --promote-briefing stages one exact active Briefing proposal. --message/--message-file and --verification define the validated canonical change message.
- `mandible auth request --type <commit|force-push|branch-delete|config-change|data-delete> --command <command> --cwd <path> --repo <ref> --title <text> --issue <id> [--spec <text>|--spec-file <file>] [--no-watch]` - Submit an explicit non-merge command for human approval. No Git preparation or command inference occurs. Merge-only flags are refused; submission never executes the command. The existing approval and execution permissions still apply.
- `mandible auth withdraw <request-id> --reason <text> --expected-revision <n> --expected-custody-generation <n> [--json]` - Withdraw only the caller's own pending request using the exact originating credential or session. The durable request and lifecycle history remain intact.
- `mandible auth candidate-repair inspect|apply <request-id> [--expected-revision <n> --expected-custody-generation <n> --expected-current-snapshot-sha256 <sha256>] [--operator-recovery] [--json]` - Inspect a pending merge request for candidate-only lifecycle snapshot drift, then append a guarded recovery snapshot only when exact custody, revision, reviewed fields, actions, protected-base history, and canonical candidate computations still match. Inspection is read-only; apply requires the three values returned by inspection. Ordinary lifecycle compare-and-swap remains strict.
- `mandible auth replay-archives <request-id> [--json]` - Replay Codex thread archive attempts for a completed successful merge auth request without rerunning the merge or deferred issue actions.
- `mandible work-unit claim --issue <id> --repo <repo> [--branch <branch>] [--parent-branch <branch>] [--kind solo|partition|integration] [--session <id>] [--graceful]` - Create or reuse a branch-based work unit using explicit mechanism inputs only. --graceful makes daemon-unreachable failures non-fatal.
- `mandible work-unit activate --issue <id> --repo <repo> [--branch <branch>] [--session <id>] [--worker] [--graceful]` - Mark the matching work unit committed, or auto-claim it in committed state, using explicit mechanism inputs only. --worker explicitly binds the caller's ambient Codex thread as the implementation worker authorized for direct post-merge archival.
- `mandible work-unit find --repo <repo> (--issue <id> | --branch <branch>) [--state <state>] [--graceful]` - Find work units by repo plus issue or branch, with optional state filtering.
- `mandible work-unit resolve --id <work-unit-id> [--auth-request-id <id>] [--graceful]` - Patch a work unit to resolved after a successful merge, optionally linking the auth request.
- `mandible work-unit release --issue <id> --repo <repo> [--graceful]` - Release active work units for an abandoned issue/repo lane without encoding worktree layout policy.
- `mandible work-unit custody-assume --id <work-unit-id> --expected-generation <n> --reason <text> [--parent-role-checkpoint <id>] [--graceful]` - Transfer durable work-unit custody to the authenticated credential with an immutable generation receipt. Integration handoff by an agent requires its audited parent-role checkpoint; solo recovery and displacement of a live integration holder are operator-only.
- `mandible trash list|create|restore|gc` - List, snapshot/remove, restore, or expire reversible branch/worktree trash custody. Create accepts a canonical-project-resolvable ref and reports when the removed worktree path can no longer be used.
- `mandible issue-file path [cwd]` - Resolve the git-root .issue helper file path for a caller-supplied or current working directory.
- `mandible issue-file read [cwd]` - Read newline-delimited issue refs from the git-root .issue helper file. Blank lines and # comments are ignored.
- `mandible issue-file write [--cwd <path>] <issue>...` - Write newline-delimited issue refs to the git-root .issue helper file for policy wrapper auto-discovery.
- `mandible commit trailer [issue...]` - Render Mandible-Issue trailers for explicit issues, or from the nearest worktree .issue file when no issues are passed.
- `mandible session link-issue <session-id> --issue <id> --repo <repo> [--repo-name <name>] [--graceful]` - Link an existing Mandible session to an issue/repo pair through the supported client surface.
- `mandible conversations star <conversation-ref|--current> [--json]` - Star exactly one durable conversation resolved by exact conversation id, exact provider session id, or the ambient provider session.
- `mandible conversations unstar <conversation-ref|--current> [--json]` - Unstar exactly one durable conversation resolved without prefix ambiguity.
- `mandible conversations tag add <conversation-ref|--current> <tag...> [--json]` - Append ordered, trimmed, exact-case-deduplicated tags to one durable conversation.
- `mandible conversations tag rm <conversation-ref|--current> <tag...> [--json]` - Remove exact-case tags from one durable conversation.
- `mandible conversations comment <conversation-ref|--current> -m <markdown> [--json]` - Append Markdown to durable conversation notes with one blank-line separator; existing notes are never overwritten.
- `mandible db query <sql> [--limit N] [--json]` - Run one row-returning SQL statement against the live ledger database over a connection SQLite holds read-only. This is the supported way to run arbitrary counts and joins the structured commands do not cover. It reads the write-ahead log, so results are current; opening the database file directly with a `?immutable=1` URI skips the -wal file and silently returns a stale snapshot, and this command cannot be pointed at one. Statements that write, or that return no rows, are refused. Rows are capped at 500 unless --limit says otherwise, and truncation is always reported.
- `mandible db tables|schema [table]|info [--json]` - List ledger tables and views, print their exact CREATE statements, or report the open database's path, size, journal mode, and write-ahead-log bytes. Same read-only connection as `mandible db query`; these replace the sqlite3 dot-commands so exploring the schema never requires opening the database file by hand.
- `mandible artifact ingest <path...> [--project <project>] [--commit <git-ref>] [--artifact <artifact-ref>] [--git|--managed] [--blob-only] [--json]` - Record logical artifact versions by registered source. --commit reads tracked Git objects from a registered project without checkout; paths are repository-relative and --project accepts friendly refs. Historical ingestion retains the current source and requires unique current/historical lineage, or --artifact when a former path was reused. Host-visible multi-path ingestion uses one atomic metadata request; all paths are validated and authorized before writes. Exact retries are unchanged. Multi-path upload, file-RPC, and blob-only modes retain per-item requests and results; they are not atomic. --commit requires host-visible repository access over HTTP. Each version has one authority: git (verified canonical project/full commit/path/hash with retained Git commit), or managed (verified Mandible stored bytes). Clean tracked files default to git; other inputs use managed. --git rejects uncommitted inputs. Copy, mutable-file, external and hash-only custody are not accepted. Current source and provenance never override saved-version custody.
- `mandible artifact move <artifact-ref> [--project <project>] [--path <path>] [--if-revision <n>] [--reconcile] [--json]` - Change source registration in one transactional request. Omitted fields retain current values; request at least one field. Friendly project refs resolve on the server. Requires artifact, owner, current-source and destination write access; preserves filesystem, ownership and history. Optional --if-revision rejects stale state, occupied destinations fail, and no-op moves are unchanged. --reconcile explicitly resolves legacy source ambiguity.
- `mandible artifact source show <artifact-ref> [--json]` - Inspect one canonical artifact's registered current source, revision, and reconciliation status.
- `mandible artifact source move <artifact-ref> --expected-revision <n> --source <json> [--reconcile] [--json]` - Move a registered source with an exact prior revision guard. Source JSON is repo (canonical project_id and relative path), local (absolute path), or managed (producer key). Requires write access to the artifact and old/new source projects; preserves ownership and historical versions. --reconcile explicitly resolves a migration reconciliation requirement for this exact identity.
- `mandible artifact format <ref> [--as id|url|markdown|full] [--label <text>] [--json]` - Resolve an artifact identity and render its ambiguity-safe short ref by default, or an HTTP URL, Markdown hyperlink, full canonical id, or structured JSON.
- `mandible briefing create <artifact-version-ref> --title <text> [--description <text>] [--comparison-base <artifact-version-ref>] [--briefing <briefing-ref> | --reason <text>] [--json]` - Bind exactly the named Artifact version to a Briefing. Active Briefings for the same logical Artifact block default creation and return reuse/add-round guidance; --briefing targets one candidate, while --reason creates a separate identity with an authenticated durable receipt. Archived candidates are advisory, and logical Artifact or series refs never resolve to latest.
- `mandible briefing rename <briefing-ref> --title <text> [--json]` - Rename one existing Briefing in place without changing its identity, membership, rounds, responses, annotations, or submissions. Human use requires the configured operator; agent use requires a durable active-agent token and retains the configured operator visibility boundary.
- `mandible briefing describe <briefing-ref> (--description <text>|--clear) [--json]` - Set or clear one Briefing purpose/result description without changing its identity, title, membership, rounds, responses, annotations, or submissions.
- `mandible briefing archive <briefing-ref> [--json]` - Hide one Briefing from default collection and bundle projections without deleting its identity, rounds, artifacts, responses, annotations, or submissions. Human use requires the configured operator; agent use requires a durable active-agent token.
- `mandible briefing restore <briefing-ref> [--json]` - Restore one archived Briefing to default collection and bundle projections with its identity and review history unchanged. Human use requires the configured operator; agent use requires a durable active-agent token.
- `mandible briefing bundle create --name <name> [<briefing-ref>...] [--sharing-reason <text>] [--json]` - Create a stable named Briefing bundle whose optional initial Briefing membership preserves the supplied order. Active cross-collection sharing requires an explicit reason recorded with authenticated provenance.
- `mandible briefing bundle add <bundle-ref> <briefing-ref> [--sharing-reason <text>] [--json]` - Append one existing Briefing to a bundle without changing that Briefing or its rounds.
- `mandible briefing bundle replace <bundle-ref> [<briefing-ref>...] [--layout <json>] [--sharing-reason <text>] [--json]` - Atomically replace an existing Briefing bundle's canonical ordered layout. Flat Briefing refs remain supported; --layout accepts direct Briefings and one-level named subgroups. Human use requires the configured operator; agent use requires a durable active-agent token and retains the configured operator visibility boundary.
- `mandible briefing bundle rename <bundle-ref> --name <text> [--json]` - Rename one existing Briefing bundle in place without changing its identity or ordered membership. Human use requires the configured operator; agent use requires a durable active-agent token and retains the configured operator visibility boundary.
- `mandible briefing bundle delete <bundle-ref> [--json]` - Delete only an empty standalone Briefing bundle. Active group placement and retained disposition, review, or composition history block deletion; members are never cascaded. Human use requires the configured operator; agent use requires a durable active-agent token.
- `mandible briefing bundle show <bundle-ref> [--json]` - Show one Briefing bundle and its manually ordered Briefing membership.
- `mandible briefing group create --key <key> --name <name> [--current <bundle-ref>] [<proposal-bundle-ref>...] [--sharing-reason <text>] [--json]` - Create a Briefing group with an immutable lower-kebab active key, optional explicit Base bundle, and ordered active proposals. Omitting --current does not infer a Base bundle.
- `mandible briefing group add <group-ref> <bundle-ref> [--sharing-reason <text>] [--json]` - Append one existing Briefing bundle as a proposed update; a bundle belongs to at most one group.
- `mandible briefing group configure <group-ref> --current <bundle-ref|none> [<proposal-bundle-ref>...] [--sharing-reason <text>] [--json]` - Configure initial Base state and the complete ordered active-proposal list. Once a Base exists, ordinary configuration cannot replace or clear it; use guarded promotion or disposition.
- `mandible briefing group archive <group-ref> [--json]` - Archive one Briefing group without archiving its bundles or member Briefings. A group that owns a destination cannot be archived.
- `mandible briefing group restore <group-ref> [--json]` - Atomically restore one archived Briefing group; active key and placement conflicts fail and leave it archived.
- `mandible briefing group promote <group-ref> --expected-base <bundle-ref> --proposal <bundle-ref> --auth-request <request-ref> --merge-head <sha> [--json]` - Guardedly apply or replay one completed successful merge transition. The exact auth request, merge head, expected prior Base, group, and active proposal must match; convergence must have succeeded. Retries are no-ops and drift fails closed.
- `mandible briefing group review <group-ref> --expected-base <bundle-ref> --proposal <bundle-ref> [--destination-changes <json>] [--json]` - Preview the exact configured-human review candidate and binding digest, including full Base and proposal layouts plus compare-and-swap destination changes.
- `mandible briefing group accept <group-ref> --expected-base <bundle-ref> --proposal <bundle-ref> --binding-digest <sha256> [--destination-changes <json>] [--json]` - Accept one exact Mandible-custodied manual or recurring proposal through the configured human operator. The digest binds Base, full layouts, frozen bytes and reviews, and destination changes; exact replay is a no-op and drift fails closed.
- `mandible briefing group reject <group-ref> --expected-base <bundle-ref> --proposal <bundle-ref> --binding-digest <sha256> [--destination-changes <json>] [--json]` - Reject one exact Mandible-custodied manual or recurring proposal through the configured human operator while preserving Base, proposal custody, review submissions, and immutable disposition history.
- `mandible briefing group destination bind <group-ref> <logical-artifact-ref> [--json]` - Legacy operator binding for an already placed document. For agent-operated published reports, use destination place with expected owner and Base state.
- `mandible briefing group destination place <group-ref> <logical-artifact-ref> --briefing <briefing-ref> --operation-key <key> --expected-owner <group-ref|none> --expected-target-base <bundle-ref|none> [--expected-source-base <bundle-ref|none>] [--route-file <manifest.json>] [--json]` - Directly place or move one published report and bind its destination, optionally installing one route in the same transaction. Requires a durable active agent or operator credential and write access to the logical Artifact's unambiguous canonical project. Exact retries are unchanged; owner and Base drift fail closed.
- `mandible briefing report update <briefing-ref> <artifact-version-ref> --operation-key <key> --expected-round <round-id> --expected-version <artifact-version-ref> [--json]` - Append one exact Artifact version as the Current round of a routed published report. Requires project write access; exact retries are unchanged and stale Current state fails closed. Reviewed-document proposals are unaffected.
- `mandible briefing group rename <group-ref> --name <text> [--json]` - Rename one stable Briefing group without changing its ordered proposed updates. Human use requires the configured operator; agent use requires a durable active-agent token.
- `mandible briefing group show <group-ref> [--json]` - Show one stable Briefing group with its distinct Base, ordered active proposals, and retained disposition history.
- `mandible briefing route inspect [<route-key>] [--json]` - Inspect authorized Briefing routes in stable key order, including the destination owner's currently derived group and every immutable template version. Requires a durable agent or operator token and project write access.
- `mandible briefing route plan <manifest.json|-> [--json]` - Resolve and validate one mandible-briefing-destination-routes@3 manifest without mutation. Each route explicitly selects reviewed-document or published-report semantics. Group ownership is derived from the logical Artifact destination map; identity, downgrade, and immutable-template drift fail closed.
- `mandible briefing route apply <manifest.json|-> [--json]` - Atomically reconcile one validated destination-route manifest with project write access for every logical Artifact. Configuration updates require expected_revision from route plan. Exact replay is idempotent. Recurring publication remains POST /api/briefings/runs.
- `mandible instructions install [--target <file>] [--worktree <path>] [--force]` - Refresh configured instruction targets, or update one explicit target. Configured targets support managed-block and standalone modes; tracked protected-branch writes are refused unless --force is explicit.
- `mandible instructions targets list|add|rm <path> [--mode managed-block|standalone]` - Configure where the generated Mandible instruction fragment is written.
- `mandible instructions post-export get|set|clear <command>` - Configure an optional command to run after instruction targets refresh, such as a module compiler.
- `mandible project list [--json]` - List canonical projects with keys, display names, remotes, checkouts, and issue counts.
- `mandible project show <ref> [--json]` - Resolve a project by key, id, work_repo_id, checkout root, remote, or display name and print its registry record.
- `mandible project add --key <k> [--display <name>] [--remote <url>] [--root <path>] [--namespace remote|upstream|local]` - Register a canonical project; optionally register its first checkout.
- `mandible project update <ref> [--key <k>] [--display <name>] [--remote <url>] [--namespace <p>]` - Update fields on an existing project registry entry.
- `mandible project add-checkout <ref> --root <path> [--work-repo-id <id>] [--default-branch <b>]` - Register or update a checkout for a project.
- `mandible project update-checkout --root <path> --project <ref> [--work-repo-id <id>] [--default-branch <b>]` - Update or register a checkout by root path, choosing its project.
- `mandible project audit [--json]` - Read-only registry audit: duplicate display names, local projects, numbered path-derived repo ids, ambiguous roots, missing keys.
- `mandible project repair [--apply] [--merge <src> <dst>] [--json]` - Guarded registry normalization: backfill keys and optionally merge duplicate projects (dry run unless --apply).
- `mandible user setup [--slug <s>] [--name <n>] [--email <e>] [--agents] [--json]` - Idempotently create or update the local human operator and record its user id in settings; --agents deliberately provisions the built-in agent users and bindings. When GLOBAL git config sets user.signingkey and it resolves to a readable public key, setup also registers it as the operator's ssh_key credential (idempotent; never duplicates an active fingerprint), which protected-merge attestation requires; a key configured only in the current repository is reported, never auto-registered. Migrations never create either the operator or agent users.
- `mandible user whoami [--json]` - Print the client identity the daemon resolves for the calling request: user, evidence method, credential label, and client-auth mode. Reports an unauthenticated caller rather than failing.
- `mandible user list [--kind <k>] [--status <s>] [--json]` - List registry users, optionally filtered by kind (human|agent|system|external) or status (active|retired).
- `mandible user show <ref> [--json]` - Resolve a user by id or slug and print it with its credentials and bindings.
- `mandible user update <ref> [--name <n>] [--email <e>] [--status active|retired] [--json]` - Update mutable fields on a user (display name, email, status).
- `mandible user credential add <ref> (--type <t> --fingerprint <f> [--public-material <m>] | --from-git-signingkey) [--label <l>] [--json]` - Add an immutable credential (ssh_key|yubikey_recipient|delegated_ssh_key|api_token), or derive an ssh_key credential from git user.signingkey. At most one active credential per fingerprint; no private key material is accepted.
- `mandible user credential revoke <id> [--json]` - Revoke a credential. Credentials are immutable: revoke then add, never mutate a fingerprint; revoked rows keep their historical references.
- `mandible user credential list <ref> [--all] [--json]` - List a user's active credentials, or all including revoked with --all.
- `mandible user token mint <ref> [--label <l>] [--store [--service <name>]] [--json]` - Mint a per-user bearer token. Without --store the raw token is printed once and never again. With --store it is written straight to the OS secret store and not printed: service defaults to mandible-operator for the human operator and mandible-agent-<app> for an agent user (its shortest active app_name binding), account is the user slug, and storing again rotates the item in place. macOS keychain is the only backend today; other platforms fail visibly.
- `mandible user binding add <ref> --type <t> --value <v> [--scope <s>] [--json]` - Add a claimed binding (app_name|provider_session_env|process_pattern|git_author_email|external_author). Bindings are claimed aliases only and never produce verified evidence.
- `mandible user binding rm <id> [--json]` - Remove a claimed binding by id.
- `mandible user binding list <ref> [--json]` - List a user's claimed bindings.
- `mandible user group add|rm|members` - Create or remove custom groups and list or deliberately update idempotent group membership.
- `mandible user grant add|rm|list` - Manage direct user or group project-role and global-capability grants.
- `mandible user access <user> <project> [--json]` - Report a user's effective project role and global capabilities, including group grants and operator implicit admin.

## Commit Trailers

- `Mandible-Issue: <ref>` is a work-tracking reference link.
- `Closes-Mandible-Issue: <ref>` is an explicit closure signal.
- Commit trailers are optional interface metadata; commits without trailers are valid but unlinked.

## Authored Markdown References

- Authored ledger Markdown issue refs use `[issue:<id>]` or `[issue:<project>/<id>]`. These refs create normal text-reference relationships.
- Authored ledger Markdown comment refs use `[comment:<issue>#<comment>]` or `[comment:<project>/<issue>#<comment>]`; `[comment:#<comment>]` is a local issue UI shortcut, not a relationship-ref form.
- Relationship type names such as `references`, `resolves`, `fixed_by`, `blocks`, and `tests` are `mandible issue link --type` values, not authored Markdown tags. Do not write `[references:<id>]`, `[closes:<id>]`, or similar relationship-name bracket refs.
- Artifact refs are typed by meaning: `[artifact:<short-id>]` names a logical artifact, `[artifact-version:<short-id>]` pins one version, `[artifact-series:<short-id>]` follows a living series (or `[artifact-series:<short-id>@<version>]` pins its numbered version), and `[artifact-blob:<short-hash>]` names immutable bytes only. Current producers use ambiguity-safe short refs and must never emit legacy `[artifact:sha256:<hash>]` refs.
- For user-facing artifact links, use `mandible artifact format <ref> --as markdown` instead of constructing routes by hand. Use `--as url`, `--as id`, or `--as full` only when that output is specifically needed; do not present a blob as though it were a logical artifact.
- Auth requests have no authored Markdown bracket tag such as `[auth:<id>]`. Link them through `mandible auth request`, auth issue links, or normal issue refs when describing the related work.

## Auth Requests

- Protected-branch merges are asynchronous: submit an auth request, stop, and let the user approve in Mandible.
- Approval and merge execution are user actions. Agents do not approve, merge, or bypass the auth queue.
- Multiple pending merge requests may coexist when they are pairwise independent. Run `mandible auth check` before submitting when unsure; submission rejects clashes with file-level conflict context. Planned related branches still integrate first.
- Auth request rows are durable reviewed records. The operator may reject a pending request or use an audited recovery path. Ordinary withdrawal, revision, and replacement authority follows the request-bound delivery work unit's current user and active credential, not a provider session. Every mutation is guarded by lifecycle revision and custody generation. Changed reviewed bytes require explicit atomic supersession with exact terminal carry-or-dispose handling for every staged action. Delete and dismiss are not lifecycle operations.
- A request may carry one canonical change message: the agent authors the outcome line, a `Why:` paragraph, and optional `Caveats:`, while the CLI owns the `Merge <branch>: ` subject prefix, the `Verification:` section, and the trailers. Trailers are reference-only `Mandible-Issue:` lines for every --issue and --closes-issue ref; a canonical message never carries `Closes-Mandible-Issue:`, so closure is carried solely by the structured issue_closures field and a frozen signed message can never disagree with the authorization that runs. The daemon validates that envelope against the structured fields before digesting, stores the canonical bytes with their SHA-256, and freezes both once the request leaves pending; `mandible auth merge` verifies that digest against the exact stored bytes and commits them, or aborts. Without a message the merge keeps git's own default merge message.

## Coordination

- The umbrella issue is the coordinator; sessions are disposable role holders.
- Umbrella membership is the set of `parent_child` relationship edges from the umbrella to its children, created by `mandible umbrella adopt` or `mandible issue link --type parent_child` and removed by `mandible issue unlink`. Umbrella bodies carry the plan and rationale, not a membership table; read children and their live state from `mandible umbrella status` or the issue's children shelf in the Mandible app.
- Delegation manifests are stored as `delegation-manifest` checkpoints and record both `digest` (the entry's own head) and `subtree_digest` (the entry plus all transitive parent_child descendants) per entry. The first payload entry is the umbrella's own head marked `self: true` — an explicit stored self baseline, not a child entry. Refresh digests with `mandible umbrella manifest refresh <umbrella>` before resuming.
- `mandible issue changed --since-issue` compares the umbrella's own issue head as well as child manifest entries, classifying each as changed, subtree_changed, unchanged, or unknown. `subtree_changed` flags work that landed on a nested sub-umbrella's descendants even when the direct child's own head is unchanged; `unknown` marks entries from manifests recorded before subtree digests existed, including the umbrella self-entry when the manifest predates the stored `self: true` baseline. Parent sessions that need their own baseline should pass `--checkpoint <id>` instead of relying on the latest shared checkpoint.
- Worker closeout records `worker_status`, branch/auth pointers, blockers, and recommended next action in the child issue.
- Mutating work-unit requests may carry allowlisted ambient provider identity as `{provider, provider_session_id}`; Mandible persists only those fields on work units and never stores the caller environment.
- Successful auth merges archive reliably linked terminal Codex worker threads. A resolved request-linked work unit can archive directly without `console_sessions` only when its `worker_provider_session_id` was explicitly bound by `work-unit activate --worker`; generic `provider` and `provider_session_id` remain ambient attribution only. Assigned stopped console or registered-session links remain valid. Live parent-role holders and active sessions are not archived. Codex resume dispatch unarchives the provider thread before sending follow-up work.
- Use `worker_status` and issue-branch links for coordination state; open/closed issue lifecycle remains separate.
- The sourceable policy-free ledger mechanism client is `cli/ledger-client.sh`; it exposes work-unit, trash-custody, issue-title, session-link, issue-file, and commit-trailer helpers for policy wrappers.

## Transports

- Default CLI transport is loopback HTTP via `MANDIBLE_BASE=http://127.0.0.1:<port>`.
- Sandboxed agents without loopback can use `MANDIBLE_BASE=file:///path/to/spool` for issue, auth submission/listing, work-unit mutation, coordinator, conversation index, repo listing, and daemon-indexed log routes.
- The file transport denies approval, merge, admin, and config routes; auth approval remains a user/dashboard action.
