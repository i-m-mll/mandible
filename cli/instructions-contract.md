# Mandible Interface Contract

Version: 14

This section is Mandible's interface contract. It describes daemon and CLI behavior that is the same for every install. It deliberately excludes user policy such as signing key names, branch naming schemes, editor preferences, and worktree tooling.

## Commands

`mandible help <command...>` prints the registered synopsis for any command below.

- {{command changes}} - Read the bounded project-scoped ledger change feed. Omit --cursor only to establish a controlled resync point, then persist and reuse next_cursor. Retention gaps, truncation, schema mismatch, and inconsistent cursors fail closed.
- {{command issue.report}} - Print deterministic issue context for handoff and planning.
- {{command issue.title}} - Resolve an issue title for caller-supplied commit-message defaults. --graceful makes daemon-unreachable failures non-fatal.
- {{command issue.list}} - List issues in the current checkout's registered repo, or --repo, as id, status, repo, and title.
- {{command issue.triage}} - Read-only issue filter with tab-separated or JSON rows, least recently updated first, capped at 50 unless --limit is given.
- {{command issue.search}} - Keyword search over issue titles, bodies, and comments across all readable projects, best match first. Each word must match a word prefix in the issue text or in one comment. Rows carry id, status, project, title, and a matched excerpt.
- {{command issue.show}} - Print the issue metadata, full body, working notes, and every comment as readable text.
- {{command umbrella.status}} - Print one deterministic coordinator fact packet: umbrella body/revision/head, latest delegation manifest, child summaries, parent-role holder state, and repo auth queue summary. Every head object carries both its own digest and an additive subtree_digest covering all transitive parent_child descendants. Child summaries include kind and child_count (direct parent_child children) so nested sub-umbrellas are visible without drilling in. --deep includes child bodies, latest closeouts/comments, branch/auth links, and issue state for parent resumption.
- {{command umbrella.adopt}} - Idempotently adopt explicit children into an umbrella, create missing parent_child edges, refresh the delegation-manifest checkpoint server-side, and return the updated umbrella status fact packet. This command and `mandible issue link --type parent_child` are the only ways to establish umbrella membership.
- {{command umbrella.manifest.refresh}} - Refresh the umbrella delegation-manifest checkpoint from current linked child issue heads server-side without changing parent_child edges, and return the updated umbrella status fact packet.
- {{command issue.parent-role.status}} / {{command issue.parent-role.assume}} / {{command issue.parent-role.release}} - Inspect, record, or step down from advisory parent-role holder state. The holder is the latest assume, until a release. --session accepts a session row id, a console session id, or an ingested provider session id (a Claude subagent's agent id included), and defaults to the caller's own provider session id (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`, `GEMINI_SESSION_ID`), else `MANDIBLE_SESSION_ID`; the daemon resolves the alias, stores every identity it reaches, and refuses an id Mandible has never seen with an actionable error. Liveness comes from the canonical session-liveness rule, which answers live, stopped, or unknown when a check cannot complete. A stopped holder is informational. A live or unknown holder changes only by its own hand: the holder re-assumes under any alias, hands the role to a successor with `assume --session <successor>` from its own session, or releases it; anyone else needs the operator's --override. Session ids are claimed attribution, so this is advisory coordination, not a security boundary. A refusal names the holder and exits 3, and --json prints the daemon's answer.
- {{command issue.heads}} - Print issue state digests for delegation manifests and resume checks. Each head carries its own digest plus an additive subtree_digest over the issue and all transitive parent_child descendants (cycle-safe, each descendant once), so drift two or more levels down a nested umbrella is detectable. A head also covers the claim, commit, and resolution of the issue's work units.
- {{command issue.changed}} - Compare current issue digests with a legacy manifest or an umbrella checkpoint. Classifies own and descendant changes; unknown baselines never report unchanged.
- {{command issue.checkpoint.add}} - Append kind-tagged structured issue state outside the comment stream. Use --payload - or --payload-file - to read JSON from stdin.
- {{command issue.checkpoint.show}} - Read kind-tagged structured issue state without parsing comments.
- {{command issue.status}} - Store an explicit worker status without changing open/closed lifecycle status. `in_progress` is not stored: readers show it while the issue has an open or committed work unit and no stored done, blocked, or pivot-needed.
- {{command issue.branch.add}} - Link a branch that has no work unit, or mark a branch superseded. Readers list an issue's branches from its open, committed, and resolved work units plus these links.
- {{command issue.link}} - Create deliberate structured issue/comment relationship edges with shared action grouping for multi-target links. Accepted types: parent_child, blocks, duplicate_of, related, references, fixed_by, caused_by, implements, tests.
- {{command issue.unlink}} - Tombstone deliberate structured issue/comment relationship edges and emit relationship removal events. Accepted types: parent_child, blocks, duplicate_of, related, references, fixed_by, caused_by, implements, tests.
- {{command issue.close}} - Close an issue with one explicit resolution. The optional --commit link is accepted only for delivered; reopening clears the resolution.
- {{command issue.open}} - Reopen a closed issue and clear its resolution. Reopening a `maintenance` issue is refused while its project has another open maintenance issue; the same applies to `comment add --reopen`.
- {{command issue.comment.add}} - Append rendered Markdown comments with real newline characters and return the issue lifecycle status; --reopen atomically reopens and comments.
- {{command issue.comment.edit}} - Edit a comment body with optional stale-base checks; comment-ref accepts a raw comment id, <issue-ref>#<ordinal>, or <issue-ref>#last. Conflicts with a stale base return exit code 3.
- {{command issue.comment.show}}, {{command issue.comment.history}} - Print a comment's current body, or its immutable revision history; --with-body includes each snapshot.
- {{command issue.description.edit}} - Edit issue descriptions while preserving body revision history.
- {{command issue.description.show}}, {{command issue.description.history}} - Print the current issue description, or its immutable revision history; --with-body includes each snapshot.
- {{command issue.revision.show}}, {{command issue.revision.diff}} - Print one text revision, or diff two revisions of the same description, comment, or working notes; --force allows different entities.
- {{command issue.new}} - Create an issue with one required concrete canonical kind. New issues cannot omit the kind or use unknown; priority defaults to normal; labels remain independent metadata. A project may have at most one open `maintenance` issue: creating a second one is refused with the existing issue's ID, so comment there instead.
- {{command issue.work-notes.show}}, {{command issue.work-notes.edit}}, {{command issue.work-notes.clear}}, {{command issue.work-notes.history}} - Read, replace, clear, or inspect immutable history for the issue's current working notes. Edits and clears use the issue PATCH API with an optional expected working-notes revision.
- {{command issue.kind.set}} - Set the canonical issue kind through the existing issue PATCH API; kind is independent from labels. Changing an open issue to `maintenance` is refused when its project already has an open maintenance issue.
- {{command issue.priority.set}} - Set the issue priority through the existing issue PATCH API. Every issue has one of low, normal, high, or urgent.
- {{command issue.label.add}} / {{command issue.label.rm}} - Add or remove one free-form label; labels never mirror or mutate canonical issue metadata.
- {{command auth.list}} - Find existing auth requests before submitting duplicates.
- {{command auth.show}} - Print one auth request with its protected-base history audit: base commits since the newest recorded Mandible merge that are neither Mandible merges nor signed with an operator hardware key (`ssh_key`).
- {{command auth.check}} - Report whether a merge is clean against the target and queued pairwise-independent requests.
- {{command auth.clearance.create}}, {{command auth.clearance.list}}, {{command auth.clearance.show}}, {{command auth.clearance.revoke}}, {{command auth.clearance.execute}} - Manage immutable operator-issued protected-merge clearances. Prospective creation requires an exact durable agent, canonical project, protected base, issue and/or head, expiry, and bounded use count; a selected request is optional provenance and prefill. Execution requires the requester's exact verified credential provenance.
- {{command auth.request}} - Submit protected-branch auth work. --space-publication binds an exact frozen Spaces publication row to its request atomically. Each merge request binds atomically to exactly one committed issue-linked delivery work unit owned by the authenticated durable credential. Use --issue for reference context and --closes-issue only for intended closure. --supersedes atomically replaces the exact pending request on the same work unit, project, head, and protected target, guarded by lifecycle revision and custody generation; every staged predecessor action is terminally carried or explicitly dropped with a reason. --promote-briefing stages one exact active Briefing proposal. Every approval request, including a supersession, requires an authored Description via --message or --message-file (API: commit_message). Non-merge Descriptions are explanatory Markdown. Merge requests additionally require --verification; the same Description becomes the validated exact canonical Git message. Git-only flags apply only to merge requests. Requests carry no separate spec: state any post-merge manual step under the message's Caveats, and link a substantial design to the issue as an artifact.
- {{command auth.request.command}} - Submit an explicit non-merge command for human approval. No Git preparation or command inference occurs. Merge-only flags are refused; submission never executes the command. The existing approval and execution permissions still apply.
- {{command auth.withdraw}} - Withdraw only the caller's own pending request using the exact originating credential or session. The durable request and lifecycle history remain intact.
- {{command auth.candidate-repair.inspect}} / {{command auth.candidate-repair.apply}} - Inspect a pending merge request for candidate-only lifecycle snapshot drift, then append a guarded recovery snapshot only when exact custody, revision, reviewed fields, actions, protected-base history, and canonical candidate computations still match. Inspection is read-only; apply requires the three values returned by inspection. Ordinary lifecycle compare-and-swap remains strict.
- {{command auth.acceptance.run}} / {{command auth.acceptance.show}} - Rerun or read daemon-run candidate acceptance of a pending runtime self-update merge request. Acceptance and the built-in post-merge rebuild apply when the server-captured change report touches production source paths from scripts/build-revision.mjs, including build and acceptance inputs; old and new paths both count. Documentation-only changes outside those paths skip acceptance, the built-in rebuild, and its restart signals; other configured hooks still run. Missing or head-mismatched reports remain gated. The daemon runs acceptance automatically when an in-scope request is submitted or superseded, when its candidate is re-pinned onto a moved base (after a merge, or on the idle tick and at startup once no runtime handoff lock is held), and at startup; a newer candidate aborts the older run. A run builds and smoke-tests the exact retained candidate merge, and its result is bound to that candidate's tree, base and head. In-scope approval requires a passing result for the current candidate. `run` re-pins a stale candidate first, then keeps an open or passed run of the current candidate, otherwise starts a new one; out-of-scope requests return no acceptance.
- {{command auth.handoff.status}} / {{command auth.handoff.retire}} - Inspect the installation's runtime handoff lock, or, as the operator, retire a failed handoff lock by its exact binding digest with a reason. While the lock is held, runtime self-update checks, submissions and approvals refuse. Retirement preserves the failed journal and records the retirement beside it; it does not make the failed delivery live.
- {{command auth.retry-convergence}} - Retry failed convergence hooks using their snapshotted commands after repairing the host condition. --hook selects which failed hook receives another attempt; the merge never reruns. Complete exits zero, pending reports that the retry was admitted and is still running, and failed exits nonzero. A lost response leaves the outcome unconfirmed: inspect with mandible auth show before another explicit retry. This differs from verification-only handoff recovery.
- {{command auth.retire-delivery}} - Retire an obsolete failed builtin delivery only before publication or handoff admission. Requires current request custody (or explicit operator recovery), a reason and lifecycle/custody preconditions. The hook remains historically failed, cannot retry, and relinquishes only its own package reference after installed, selection, handoff, consumer and investigation guards pass. Ordinary maintenance owns cleanup; pending cleanup may be resumed idempotently with fresh preconditions. Never use this for an admitted handoff or to claim successful convergence.
- {{command auth.handoff.recover}} - Recover a failed runtime handoff whose exact merge generation is already live. The daemon observes the running installation for 31 seconds without rerunning the merge, a build, an installer or a restart, then records convergence, applies withheld closures and releases the lock. It requires the request's delivery work-unit credential, or the operator with --operator-recovery; a refusal leaves the failed handoff and its evidence unchanged.
- {{command auth.replay-archives}} - Replay Codex thread archive attempts for a completed successful merge auth request without rerunning the merge or deferred issue actions.
- {{command auth.action.list}} - List the issue actions staged on an auth request with their ordinals and states.
- {{command auth.action.add}}, {{command auth.action.edit}}, {{command auth.action.rm}} - Stage, replace, or remove an issue action that a merge request applies after a successful merge: comment_add, issue_close, worker_status_set, label_add, label_rm, checkpoint_add, or link_add. Actions change only while the request is pending or failed; each change is guarded by the request's lifecycle revision and custody generation and appends a lifecycle revision. issue_close is withheld until convergence succeeds.
- {{command reminder.create}} - Arm a durable one-shot reminder that posts its message to the Mandible inbox when exactly one trigger fires: a time, an issue closing, or a project's completed-merge count reaching a threshold. Retrying with the same idempotency key and arguments is unchanged; the same key with different arguments conflicts.
- {{command reminder.show}}, {{command reminder.list}}, {{command reminder.cancel}} - Inspect, list, or cancel reminders.
- {{command work-unit.claim}} - An explicit kind correction on an existing unit requires current custody and generation; integration promotion also requires the latest matching umbrella parent-role checkpoint. Integration downgrades are refused. Create or reuse a branch-based work unit using explicit mechanism inputs only. Re-recording the session or credential on a held unit obeys the custody-assume holder rule; the holder's own `--session <worker>` handoff passes. --graceful makes only daemon-unreachable failures non-fatal; daemon refusals still fail.
- {{command work-unit.activate}} - Mark the matching work unit committed, or auto-claim it in committed state, using explicit mechanism inputs only. It never takes a unit over: when another credential, or another session of the caller's credential, holds it, activation refuses with `custody_holder_live`, or `custody_holder_stopped` and the custody-assume command. --worker explicitly binds the caller's ambient Codex thread as the implementation worker authorized for direct post-merge archival.
- {{command work-unit.find}} - Find work units by repo plus issue or branch, with optional state filtering.
- {{command work-unit.resolve}} - Patch a work unit to resolved after a successful merge, optionally linking the auth request.
- {{command work-unit.release}} - Release one exact unit by ID or repository and branch, guarded by its observed generation.
- {{command work-unit.release-issue}} - Release an explicit issue snapshot; every selected unit carries its observed generation.
- {{command work-unit.custody-assume}} - Transfer durable work-unit custody to the authenticated credential with an immutable generation receipt and a comment on the unit's issue naming both holders. An active agent credential with project write access may take over a solo or partition unit whose recorded holder session has stopped; a live holder, or one whose liveness Mandible cannot establish, refuses with the holder named. --request-approval then queues a custody-transfer auth request; the operator's approval in the Mandible app transfers custody to the requesting credential. Within one credential the unit's recorded session holds it under the same rule; session ids are claimed attribution, so session-level holding is advisory coordination between cooperating agents, not a security boundary. Integration handoff by an agent requires its audited parent-role checkpoint. The operator may recover any unit directly. The generation compare-and-swap lets one of two racing takers win, and the previous holder's custody-guarded calls then fail on generation.
- {{command work-unit.custody-check}} - Read-only preview, before committing, of the holder rule that activate, claim, and custody-assume enforce. Exit 0 (`clear`): the caller holds the unit or may claim it; a caller with no session id cannot be compared with the recorded session and gets a warning instead. Exit 3 (`held`): another credential, or another session of the caller's credential, holds it and is live or of unknown liveness. Exit 4 (`takeover_available`): that holder has stopped. Every refusal names the holder and its liveness and carries the exact `takeover_command`; exit 1 means the check could not run.
- {{command trash.list}}, {{command trash.create}}, {{command trash.restore}}, {{command trash.gc}} - List, snapshot/remove, restore, or expire reversible branch/worktree trash custody. Create accepts a canonical-project-resolvable ref and reports when the removed worktree path can no longer be used. It keeps the worktree's unique ignored files in custody, skipping symlinks and rebuildable directories, and restore writes them back as ignored files; when they exceed the repo's `[trash.ignored]` size limit or include a nested repository, create refuses and removes nothing. With --merged-into, create first proves the branch merged or tree-equivalent to that target, and removes it without an entry when nothing unique remains; the response's `result` is `removed`, `trashed`, or `refused`.
- {{command issue-file.path}} - Resolve the git-root .issue helper file path for a caller-supplied or current working directory.
- {{command issue-file.read}} - Read newline-delimited issue refs from the git-root .issue helper file. Blank lines and # comments are ignored.
- {{command issue-file.write}} - Write newline-delimited issue refs to the git-root .issue helper file for policy wrapper auto-discovery.
- {{command session.link-issue}} - Link a session to an issue/repo pair. The session is a session row id, a console session id, or an ingested provider session id; the link is keyed on the provider session id when one is known, else on the console or session row id, and never creates a session row. An id Mandible has never seen is refused with the retryable `provider_session_not_ingested`.
- {{command conversations.list}}, {{command conversations.show}}, {{command conversations.search}} - List, read, or search Mandible's normalized conversation index across providers.
- {{command conversations.star}} - Star exactly one durable conversation resolved by exact conversation id, exact provider session id, or the ambient provider session.
- {{command conversations.unstar}} - Unstar exactly one durable conversation resolved without prefix ambiguity.
- {{command conversations.tag.add}} - Append ordered, trimmed, exact-case-deduplicated tags to one durable conversation.
- {{command conversations.tag.rm}} - Remove exact-case tags from one durable conversation.
- {{command conversations.comment}} - Append Markdown to durable conversation notes with one blank-line separator; existing notes are never overwritten.
- {{command conversations.lineage-gaps}} - List conversations that are children without a trustworthy parent, with counts by provider and kind. Gaps: a malformed lineage marker, a parent Mandible has not indexed, a marker whose parent disagrees with the provider's creator record, an agent-created thread with neither creator record nor marker, or a legacy prose role clarification. Warning: a child linked from the creator record alone, whose relation was assumed and whose roles are missing. Only conversations whose opening Mandible has read are judged; `--since` narrows by start time.
- {{command logs.inspect}} - Read one provider-native source transcript, the veridical record behind the conversation index, without touching the Mandible database; --parse applies normalized block filters.
- {{command db.query}} - Run one row-returning SQL statement against the live ledger database over a connection SQLite holds read-only. This is the supported way to run arbitrary counts and joins the structured commands do not cover. It reads the write-ahead log, so results are current; opening the database file directly with a `?immutable=1` URI skips the -wal file and silently returns a stale snapshot, and this command cannot be pointed at one. Statements that write, or that return no rows, are refused. Rows are capped at 500 unless --limit says otherwise, and truncation is always reported.
- {{command db.tables}}, {{command db.schema}}, {{command db.info}} - List ledger tables and views, print their exact CREATE statements, or report the open database's path, size, journal mode, and write-ahead-log bytes. Same read-only connection as `mandible db query`; these replace the sqlite3 dot-commands so exploring the schema never requires opening the database file by hand.
- {{command artifact.ingest}} - Record logical artifact versions by registered source. --project names the artifact's project and accepts friendly refs: a repository file must belong to it, and any other source takes it as its owner. --commit reads tracked Git objects from that project without checkout; paths are repository-relative. Historical ingestion retains the current source and requires unique current/historical lineage, or --artifact when a former path was reused. Host-visible multi-path ingestion uses one atomic metadata request; all paths are validated and authorized before writes. Exact retries are unchanged. Multi-path upload, file-RPC, and blob-only modes retain per-item requests and results; they are not atomic. --commit requires host-visible repository access over HTTP. Each version has one authority: git (verified canonical project/full commit/path/hash with retained Git commit), or managed (verified Mandible stored bytes). Clean tracked files default to git; other inputs use managed. --git rejects uncommitted inputs. Copy, mutable-file, external and hash-only custody are not accepted. Current source and provenance never override saved-version custody.
- {{command artifact.move}} - Change source registration in one transactional request. Omitted fields retain current values; request at least one field. Friendly project refs resolve on the server. Requires artifact, owner, current-source and destination write access; preserves filesystem, ownership and history. Optional --if-revision rejects stale state, occupied destinations fail, and no-op moves are unchanged. --reconcile explicitly resolves legacy source ambiguity.
- {{command artifact.source.show}} - Inspect one canonical artifact's registered current source, revision, reconciliation status, and version count per custody mode. An artifact has at most one source (a repo path, local path, or managed producer key), and each source belongs to at most one artifact. Ingesting from the source adds a version; ingesting a different path is refused until a source move. Mandible never reads a source on its own. For git custody the source is the repo path the artifact follows; for managed custody it is only where the file was ingested from, and that file may change or disappear without affecting saved versions.
- {{command artifact.source.move}} - Move a registered source with an exact prior revision guard. Source JSON is repo (canonical project_id and relative path), local (absolute path), or managed (producer key). Requires write access to the artifact and old/new source projects; preserves ownership and historical versions. --reconcile explicitly resolves a migration reconciliation requirement for this exact identity.
- {{command artifact.format}} - Resolve an artifact identity and render its ambiguity-safe short ref by default, or an HTTP URL, Markdown hyperlink, full canonical id, or structured JSON.
- {{command artifact.link}} - Link an artifact to an issue as references, output, evidence, or handoff. A link pins the resolved version unless --living follows the latest version.
- {{command artifact.associate}} - Associate an artifact with a canonical project; --canonical records that project as its canonical home.
- {{command artifact.resolve}}, {{command artifact.show}}, {{command artifact.versions}} - Resolve a typed ref to its artifact, show the artifact's custody and availability, or list its versions.
- {{command artifact.list}} - List artifacts filtered by repo, issue, role, or custody mode.
- {{command artifact.content}} - Print the text content a ref resolves to, or write it with --output; binary content reports metadata only.
- {{command artifact.check}} - Report whether each ref's bytes can be materialized from their custody, with reasons. Run it before relying on or handing off artifact bytes.
- {{command artifact.diff}} - Compare two artifact refs.
- {{command briefing.create}} - Bind exactly the named Artifact version to a Briefing. Active Briefings for the same logical Artifact block default creation and return reuse/add-round guidance; --briefing targets one candidate, while --reason creates a separate identity with an authenticated durable receipt. Archived candidates are advisory, and logical Artifact or series refs never resolve to latest.
- {{command briefing.rename}} - Rename one existing Briefing in place without changing its identity, membership, rounds, responses, annotations, or submissions. Human use requires the configured operator; agent use requires an active agent identity and retains the configured operator visibility boundary.
- {{command briefing.describe}} - Set or clear one Briefing purpose/result description without changing its identity, title, membership, rounds, responses, annotations, or submissions.
- {{command briefing.archive}} - Hide one Briefing from default collection and bundle projections without deleting its identity, rounds, artifacts, responses, annotations, or submissions. Human use requires the configured operator; agent use requires an active agent identity.
- {{command briefing.restore}} - Restore one archived Briefing to default collection and bundle projections with its identity and review history unchanged. Human use requires the configured operator; agent use requires an active agent identity.
- {{command briefing.bundle.create}} - Create a stable named Briefing bundle whose optional initial Briefing membership preserves the supplied order. Active cross-collection sharing requires an explicit reason recorded with authenticated provenance.
- {{command briefing.bundle.add}} - Append one existing Briefing to a bundle without changing that Briefing or its rounds.
- {{command briefing.bundle.replace}} - Atomically replace an existing Briefing bundle's canonical ordered layout. Flat Briefing refs remain supported; --layout accepts direct Briefings and one-level named subgroups. Human use requires the configured operator; agent use requires an active agent identity and retains the configured operator visibility boundary.
- {{command briefing.bundle.rename}} - Rename one existing Briefing bundle in place without changing its identity or ordered membership. Human use requires the configured operator; agent use requires an active agent identity and retains the configured operator visibility boundary.
- {{command briefing.bundle.delete}} - Delete only an empty standalone Briefing bundle. Active group placement and retained disposition, review, or composition history block deletion; members are never cascaded. Human use requires the configured operator; agent use requires an active agent identity.
- {{command briefing.bundle.show}} - Show one Briefing bundle and its manually ordered Briefing membership.
- {{command briefing.group.create}} - Create a Briefing group with an immutable lower-kebab active key, optional explicit Base bundle, and ordered active proposals. Omitting --current does not infer a Base bundle.
- {{command briefing.group.add}} - Append one existing Briefing bundle as a proposed update; a bundle belongs to at most one group.
- {{command briefing.group.configure}} - Configure initial Base state and the complete ordered active-proposal list. Once a Base exists, ordinary configuration cannot replace or clear it; use guarded promotion or disposition.
- {{command briefing.group.archive}} - Archive one Briefing group without archiving its bundles or member Briefings. A group that owns a destination cannot be archived.
- {{command briefing.group.restore}} - Atomically restore one archived Briefing group; active key and placement conflicts fail and leave it archived.
- {{command briefing.group.promote}} - Guardedly apply or replay one completed successful merge transition. The exact auth request, merge head, expected prior Base, group, and active proposal must match; convergence must have succeeded. Retries are no-ops and drift fails closed.
- {{command briefing.group.review}} - Preview the exact configured-human review candidate and binding digest, including full Base and proposal layouts plus compare-and-swap destination changes.
- {{command briefing.group.accept}} - Accept one exact Mandible-custodied manual or recurring proposal through the configured human operator. The digest binds Base, full layouts, frozen bytes and reviews, and destination changes; exact replay is a no-op and drift fails closed.
- {{command briefing.group.reject}} - Reject one exact Mandible-custodied manual or recurring proposal through the configured human operator while preserving Base, proposal custody, review submissions, and immutable disposition history.
- {{command briefing.group.destination.bind}} - Legacy operator binding for an already placed document. For agent-operated published reports, use destination place with expected owner and Base state.
- {{command briefing.group.destination.place}} - Directly place or move one published report and bind its destination, optionally installing one route in the same transaction. Requires a durable active agent or operator credential and write access to the logical Artifact's unambiguous canonical project. Exact retries are unchanged; owner and Base drift fail closed.
- {{command briefing.report.update}} - Append one exact Artifact version as the Current round of a routed published report. Requires project write access; exact retries are unchanged and stale Current state fails closed. Reviewed-document proposals are unaffected.
- {{command briefing.group.rename}} - Rename one stable Briefing group without changing its ordered proposed updates. Human use requires the configured operator; agent use requires an active agent identity.
- {{command briefing.group.show}} - Show one stable Briefing group with its distinct Base, ordered active proposals, and retained disposition history.
- {{command briefing.route.inspect}} - Inspect authorized Briefing routes in stable key order, including the destination owner's currently derived group and every immutable template version. Requires an active agent or operator identity and project write access.
- {{command briefing.route.plan}} - Resolve and validate one mandible-briefing-destination-routes@3 manifest without mutation. Each route explicitly selects reviewed-document or published-report semantics. Group ownership is derived from the logical Artifact destination map; identity, downgrade, and immutable-template drift fail closed.
- {{command briefing.route.apply}} - Atomically reconcile one validated destination-route manifest with project write access for every logical Artifact. Configuration updates require expected_revision from route plan. Exact replay is idempotent. Recurring publication remains POST /api/briefings/runs.
- {{command instructions.install}} - Refresh configured instruction targets, or update one explicit target. Configured targets support managed-block and standalone modes; tracked protected-branch writes are refused unless --force is explicit.
- {{command instructions.diff}} - Show how one instruction target, by default `~/.claude/CLAUDE.md`, differs from the current rendered fragment.
- {{command instructions.targets.list}}, {{command instructions.targets.add}}, {{command instructions.targets.rm}} - Configure where the generated Mandible instruction fragment is written.
- {{command instructions.post-export.get}}, {{command instructions.post-export.set}}, {{command instructions.post-export.clear}} - Configure an optional command to run after instruction targets refresh, such as a module compiler.
- {{command project.list}} - List canonical projects with keys, display names, remotes, checkouts, and issue counts.
- {{command project.show}} - Resolve a project by key, id, work_repo_id, checkout root, remote, or display name and print its registry record.
- {{command project.add}} - Register a canonical project; optionally register its first checkout.
- {{command project.update}} - Update fields on an existing project registry entry.
- {{command project.add-checkout}} - Register or update a checkout for a project.
- {{command project.update-checkout}} - Update or register a checkout by root path, choosing its project.
- {{command project.audit}} - Read-only registry audit: duplicate display names, local projects, numbered path-derived repo ids, ambiguous roots, missing keys.
- {{command project.repair}} - Guarded registry normalization: backfill keys and optionally merge duplicate projects (dry run unless --apply).
- {{command user.setup}} - Idempotently create or update the local human operator and record its user id in settings; --agents deliberately provisions the built-in agent users and bindings. When GLOBAL git config sets user.signingkey and it resolves to a readable public key, setup also registers it as the operator's ssh_key credential (idempotent; never duplicates an active fingerprint), which protected-merge attestation requires; a key configured only in the current repository is reported, never auto-registered. Migrations never create either the operator or agent users.
- {{command user.whoami}} - Print the client identity the daemon resolves for the calling request: user, evidence method, credential label, and client-auth mode. Reports an unauthenticated caller rather than failing.
- {{command user.list}} - List registry users, optionally filtered by kind (human|agent|system|external) or status (active|retired).
- {{command user.show}} - Resolve a user by id or slug and print it with its credentials and bindings.
- {{command user.update}} - Update mutable fields on a user (display name, email, status).
- {{command user.credential.add}} - Add an immutable credential (ssh_key|yubikey_recipient|delegated_ssh_key|api_token), or derive an ssh_key credential from git user.signingkey. At most one active credential per fingerprint; no private key material is accepted.
- {{command user.credential.revoke}} - Revoke a credential. Credentials are immutable: revoke then add, never mutate a fingerprint; revoked rows keep their historical references.
- {{command user.credential.list}} - List a user's active credentials, or all including revoked with --all.
- {{command user.token.mint}} - Mint a per-user bearer token. Without --store the raw token is printed once and never again. With --store it is written straight to the OS secret store and not printed: service defaults to mandible-operator for the human operator and mandible-agent-<app> for an agent user (its shortest active app_name binding), account is the user slug, and storing again rotates the item in place. macOS keychain is the only backend today; other platforms fail visibly.
- {{command user.token.list}}, {{command user.token.revoke}} - List a user's tokens, including revoked ones with --all, or revoke one by its credential id.
- {{command user.binding.add}} - Add a claimed binding (app_name|provider_session_env|process_pattern|git_author_email|external_author). Bindings are claimed aliases only and never produce verified evidence.
- {{command user.binding.rm}} - Remove a claimed binding by id.
- {{command user.binding.list}} - List a user's claimed bindings.
- {{command user.group.add}}, {{command user.group.rm}}, {{command user.group.members}} - Create or remove custom groups and list or deliberately update idempotent group membership.
- {{command user.grant.add}}, {{command user.grant.rm}}, {{command user.grant.list}} - Manage direct user or group project-role and global-capability grants.
- {{command user.access}} - Report a user's effective project role and global capabilities, including group grants and operator implicit admin.

## Authored Markdown References

- Authored ledger Markdown issue refs use `[issue:<id>]` or `[issue:<project>/<id>]`. These refs create normal text-reference relationships.
- Authored ledger Markdown comment refs use `[issue:<id>#<n>]` or `[issue:<project>/<id>#<n>]`, where `<n>` is the comment ordinal that `mandible issue comment show <id>#<n>` accepts; `#0` is the issue description. They link to that comment and create the same text-reference relationship as `[issue:<id>]`. Legacy `[comment:<issue>#<comment>]` text keeps working; do not write new `[comment:...]` refs.
- Authored ledger Markdown auth request refs use `[auth:<short-id>]`, resolved with the same ambiguity-safe prefix rules as `mandible auth` commands. Auth request ids are global, so there is no project-qualified form. An auth ref links readers to the request; it creates no issue relationship and never changes the request's structured issue context or closure actions, which come only from `mandible auth request` fields.
- Authored ledger Markdown Briefing refs use `[briefing:<short-id>]`, resolved with the same ambiguity-safe prefix rules as `mandible briefing` commands; the short id omits any legacy `briefing:` prefix stored in the Briefing id. Briefing ids are global, so there is no project-qualified form. A Briefing ref links readers to the Briefing itself and creates no issue relationship; cite the presented artifact version instead when the text is about the reviewed content.
- Relationship type names such as `references`, `resolves`, `fixed_by`, `blocks`, and `tests` are `mandible issue link --type` values, not authored Markdown tags. Do not write `[references:<id>]`, `[closes:<id>]`, or similar relationship-name bracket refs.
- Artifact refs are typed by meaning: `[artifact:<short-id>]` names a logical artifact, `[artifact-version:<short-id>]` pins one version, `[artifact-series:<short-id>]` follows a living series (or `[artifact-series:<short-id>@<version>]` pins its numbered version), and `[artifact-blob:<short-hash>]` names immutable bytes only. Current producers use ambiguity-safe short refs and must never emit legacy `[artifact:sha256:<hash>]` refs.
- User-facing links to issues, auth requests, artifacts, and Briefings use `https://app.mandible.localhost:19420/<kind>/<ref>`, where `<kind>` is `issue`, `auth`, `artifact`, or `briefing`; it opens the entity as a web page in the current browser. The same URL with `/r` before the kind, `https://app.mandible.localhost:19420/r/<kind>/<ref>`, opens the entity in the Mandible desktop app. An artifact's `<ref>` is its typed short ref, such as `artifact-version:<short-id>`. Other query parameters carry through to the opened view. Use `mandible artifact format <ref>` only to resolve a long or untyped artifact ref, and do not present a blob as though it were a logical artifact.

## Auth Requests

- Protected-branch merges are asynchronous: submit an auth request, stop, and let the user approve in Mandible.
- Approval and merge execution are user actions. Agents do not approve, merge, or bypass the auth queue.
- Multiple pending merge requests may coexist when they are pairwise independent. Run `mandible auth check` before submitting when unsure; submission rejects clashes with file-level conflict context. Planned related branches still integrate first.
- Auth request rows are durable reviewed records. The operator may reject a pending request or use an audited recovery path. Ordinary withdrawal, revision, and replacement authority follows the request-bound delivery work unit's current user and active credential, not a provider session. Every mutation is guarded by lifecycle revision and custody generation. Changed reviewed bytes require explicit atomic supersession with exact terminal carry-or-dispose handling for every staged action. Delete and dismiss are not lifecycle operations.
- Every merge request carries one canonical change message, and the daemon refuses one without it: the author supplies the outcome, Why paragraph, and optional Caveats; the CLI composes the subject prefix and Verification section. Issue relationships and closure actions are carried exclusively by structured request fields. Commit messages have no issue-linking or closure semantics. Canonical message bytes and their digest are frozen after approval and verified at execution.

## Coordination

- The umbrella issue is the coordinator; sessions are disposable role holders.
- Umbrella membership is the set of `parent_child` relationship edges from the umbrella to its children, created by `mandible umbrella adopt` or `mandible issue link --type parent_child` and removed by `mandible issue unlink`. Umbrella bodies carry the plan and rationale, not a membership table; read children and their live state from `mandible umbrella status` or the issue's children shelf in the Mandible app.
- Delegation manifests are stored as `delegation-manifest` checkpoints and record both `digest` (the entry's own head) and `subtree_digest` (the entry plus all transitive parent_child descendants) per entry. The first payload entry is the umbrella's own head marked `self: true` — an explicit stored self baseline, not a child entry. Refresh digests with `mandible umbrella manifest refresh <umbrella>` before resuming.
- `mandible issue changed --since-issue` compares the umbrella's own issue head as well as child manifest entries, classifying each as changed, subtree_changed, unchanged, or unknown. `subtree_changed` flags work that landed on a nested sub-umbrella's descendants even when the direct child's own head is unchanged; `unknown` marks entries from manifests recorded before subtree digests existed, including the umbrella self-entry when the manifest predates the stored `self: true` baseline. Parent sessions that need their own baseline should pass `--checkpoint <id>` instead of relying on the latest shared checkpoint.
- Worker closeout records `worker_status`, branch/auth pointers, blockers, and recommended next action in the child issue.
- Mutating work-unit requests may carry allowlisted ambient provider identity as `{provider, provider_session_id}`; Mandible persists only those fields on work units and never stores the caller environment.
- A Codex worker thread bound by `work-unit activate --worker` is archived once for each of its work units that resolves, by any path (merge request, ancestry scan, `wt merge` into a parent branch, or explicit resolve), when the thread is definitely stopped, never held a parent role, and no open or committed unit names it; unknown liveness defers to a later pass, and a failed archive retries with backoff. Generic `provider` and `provider_session_id` remain ambient attribution only. Successful auth merges also archive terminal Codex threads linked through assigned stopped console or registered sessions. Codex resume dispatch unarchives the provider thread before sending follow-up work.
- Work units are the source of an issue's branches and in-progress state; stored `worker_status` records only explicit done, blocked, or pivot-needed statements. Open/closed issue lifecycle remains separate.
- The sourceable policy-free ledger mechanism client is `cli/ledger-client.sh`; it exposes work-unit, trash-custody, issue-title, session-link, and issue-file helpers for policy wrappers.

## Session Lineage

- A child is a session another session created to do part of its work; a successor handed a goal is not a child. `conversations.parent_conversation_id` is the one lineage store, written only by ingestion.
- A subagent's parent is its provider's own record. Every other child declares its parent with the lineage marker, which is exactly line 1 of its first user message, read by every provider's parser and nowhere else:
  - `[mandible child parent=<provider>:<session-id> parent-role=<role> role=<role>]`
  - `[mandible successor predecessor=<provider>:<session-id> role=<role>]`
- `<provider>` is `claude`, `codex`, or `gemini`; `<session-id>` is the provider session or thread id (`CLAUDE_CODE_SESSION_ID`, `CODEX_THREAD_ID`); roles are lowercase role names. Fields may appear in any order, each exactly once. A line that starts with `[mandible` and does not parse is malformed and is never guessed at.
- When the provider records who created the thread (a Codex `create_thread` delegation envelope's `source_thread_id`), that record is the parent and the marker supplies the relation and roles; a marker naming a different parent is flagged. A child is the default relation: a thread with a creator record and no marker is linked as a child with a warning, so a successor created this way must carry the `successor` marker, which keeps it out of the child store.
- A child is linked when its parent is indexed, whichever arrives first; until then it is an unresolved-parent lineage gap. Mandible logs `conversation_lineage_gap` once when ingestion creates a gap.
- A launch that writes a child's or successor's first message puts the marker on its line 1, derived from the launching session's id and the roles.

## Transports

- Ordinary local CLI access uses the owner-only Unix socket `~/.cache/mandible/local-api/production.sock`, without a bearer token or expiring session. `MANDIBLE_SOCKET` selects an explicit absolute socket path. Connection failure never falls back to HTTP.
- Provider and task IDs are attached automatically as claimed attribution. They are not credentials. Managed clients with missing or conflicting attribution cannot become the human operator.
- Protected request lifecycle, durable custody, credential administration, and explicit execution routes deliberately use the durable Keychain credential. Ordinary calls ignore inherited `MANDIBLE_TOKEN`; protected calls never retry a rejected mutation with stronger authority.
- Explicit noncanonical `MANDIBLE_BASE=http://127.0.0.1:<port>` selects credentialed HTTP. Use `MANDIBLE_TRANSPORT=http` to explicitly select HTTP at the canonical browser origin. Browser Host, Origin, and CSRF protections remain enabled. Preview instances have separate sockets and retain their effect limits.
- Sandboxed agents without loopback can use `MANDIBLE_BASE=file:///path/to/spool` for issue, auth submission/listing, work-unit mutation, coordinator, conversation index, repo listing, and daemon-indexed log routes.
- The file transport denies approval, merge, admin, and config routes; auth approval remains a user/dashboard action.
