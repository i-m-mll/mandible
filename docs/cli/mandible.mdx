# mandible CLI

The `mandible` command is a dispatcher that routes to subcommands. HTTP subcommands use the registered production origin at `https://app.mandible.localhost:19420`; sandboxed clients may use file RPC.

## Global Environment

| Variable | Description |
|---|---|
| `MANDIBLE_PORT` | Daemon backend port (default: `29420`) |
| `MANDIBLE_BASE` | Daemon base URL (default: `https://app.mandible.localhost:19420`) |
| `MANDIBLE_SESSION_ID` | Current session ID (set by `mandible wrap`) |
| `MANDIBLE_DB` | Database path (default: `~/.cache/mandible/mandible.db`) |

## Restart availability temporary failures

Before uploading an operational mutation, the CLI checks a small versioned
receipt under the Mandible cache root. A fresh, instance-matching self-merge
receipt returns immediately with temporary-failure status (exit `75`, or `503`
from capture helpers) and does not enter the ordinary HTTP retry loop.

Structured output uses `error: "mandible_restarting"`, `retryable: true`, and
`request_sent: false`. The last field is emitted only because this check occurs
before request upload. `phase` is `rebuilding` for the full admission-closed
window or `shutdown` after the exact restart action begins. Available estimates
include `retry_after_seconds` (or `eta_exceeded_seconds`), `average_seconds`, and
`sample_count`. An absent, stale, malformed, future-version, or unrelated-instance
receipt is ignored; it never turns arbitrary daemon unavailability into a known
self-merge.

The receipt keeps rebuild-start-to-ready, exact-shutdown-to-ready, and
ready-to-warm samples separately. Only the first two can estimate blocking;
`warm` remains diagnostic and never delays mutation readiness. A mutation whose
body may already have reached a transport keeps its existing unknown-outcome,
do-not-replay handling instead of being reclassified as `request_sent: false`.

## Subcommands

### mandible wrap

Process lifecycle wrapper for agent sessions. Registers the session with Mandible on start and deregisters when the wrapped process exits.

```
mandible wrap [--app NAME] [--id ID] -- command [args...]
```

**Options:**

| Flag | Description |
|---|---|
| `--app NAME` | Application name (auto-detected from command if omitted) |
| `--id ID` | Session UUID (auto-generated if omitted) |

**Examples:**

```bash
mandible wrap -- claude --dangerously-skip-permissions
mandible wrap -- codex exec "fix the bug"
mandible wrap --app codex --id my-session-123 -- codex
```

**Behavior:**

1. Infers `app` from the command basename if not specified (`claude*` -> `claude`, `codex*` -> `codex`).
2. Generates a UUID session ID if not provided.
3. Exports `MANDIBLE_SESSION_ID` and `AI_AGENT_SIGNING=1` for child processes.
4. Detects `--dangerously-skip-permissions` flags and exports `CLAUDE_SKIP_PERMISSIONS=1`.
5. Collects environment data: terminal emulator, multiplexer, git branch, multiplexer pane metadata.
6. Registers the session via `POST /api/sessions/register`.
7. Spawns a background watcher that deregisters via `PATCH /api/sessions/:id/end` when the process exits.
8. Uses `exec` to replace itself with the wrapped command (full TTY passthrough).

### mandible task

Set the task description on the current session.

```
mandible task "Fixing SSE bugs"
mandible task --clear
```

Walks the PPID chain to find an active session via `GET /api/sessions/by-pid/:pid`, then patches the `task` field via `PATCH /api/sessions/:id`.

### mandible inbox

Query and manage the session inbox.

```
mandible inbox                         Pretty-print pending items for current branch
mandible inbox check                   Machine-friendly one-liner (for hooks)
mandible inbox add "text"              Create Mandible reminder issue with 'reminder' label
mandible inbox ack <type> <id>         Acknowledge an item (type: continuation|auth_result)
mandible inbox watch <request-id>      Poll until auth request resolves (timeout: 30 min)
```

**Subcommands:**

| Command | Description |
|---|---|
| *(none)* | Pretty-print continuations, auth results, and open issues for the current branch |
| `check` | Machine-friendly summary line for use in shell hooks |
| `add "text"` | Create a Mandible issue with the `reminder` label |
| `ack <type> <id>` | Acknowledge a continuation or auth result |
| `watch <id>` | Poll `GET /api/auth/request/:id` every 5 seconds until resolved or timeout |

### mandible issue

Issue management wrapper around the Mandible ledger.

```
mandible issue new -t <title> -m <body> --kind bug|feature|umbrella|maintenance|experiment|tracker [--priority low|normal|high|urgent] [--label <label>]...
mandible issue list [--status open|closed|all]
mandible issue show <id>
mandible issue report <id> [--json]
mandible issue triage [--repo <repo-ref>] [--status open|closed|all] [--resolution <resolution>] [--kind <kind>] [--priority <priority>] [--label <label>] [--stale-days N] [--limit N] [--json]
mandible issue search <words>... [--repo <project>] [--status open|closed|all] [--limit N] [--json]
mandible issue close <id> --resolution delivered|duplicate|wontfix [--commit <sha>]
mandible issue open <id>
mandible issue description show <issue-ref> [--json]
mandible issue description edit <issue-ref> -m <body> [--base-revision <rev>] [--base-body-hash <hash>]
mandible issue description history <issue-ref> [--json] [--with-body]
mandible issue work-notes show <issue-ref> [--json]
mandible issue work-notes edit <issue-ref> -m <text> [--base-revision <rev>]
mandible issue work-notes clear <issue-ref> [--base-revision <rev>]
mandible issue work-notes history <issue-ref> [--json] [--with-body]
mandible issue kind set <issue-ref> bug|feature|umbrella|maintenance|experiment|tracker|unknown
mandible issue priority set <issue-ref> low|normal|high|urgent
mandible issue comment add <issue-ref> -m <text>
mandible issue comment show <comment-ref> [--json]
mandible issue comment history <comment-ref> [--json] [--with-body]
mandible issue revision show <revision-id> [--json]
mandible issue revision diff <old-revision-id> <new-revision-id> [--force]
mandible issue label add <id> <label>
mandible issue label rm <id> <label>
```

**Subcommands:**

| Command | Description |
|---|---|
| `new` | Create a new issue with title, body, a required concrete kind, an optional priority (default `normal`), and optional labels |
| `list` | List issues (default: open only) |
| `show` | Show issue details |
| `report` | Print deterministic issue context for agent handoff. This is factual metadata, comments, relationships, work units, sessions, auth requests, timeline, conflicts, and sync state; it does not synthesize remaining work. |
| `triage` | Filter issues by canonical status, resolution, kind, priority, free-form label, stale age, and limit for deterministic review queues. |
| `search` | Keyword search over titles, bodies, and comments across all readable projects, best match first, with a matched excerpt. |
| `link` | Create deliberate structured issue/comment relationship edges without fabricating comments. |
| `unlink` | Tombstone deliberate structured issue/comment relationship edges and record removal events. |
| `close` | Close an issue with an explicit `delivered`, `duplicate`, or `wontfix` resolution. An optional `--commit <sha>` link is supported only for `delivered`; that resolution adds a ledger comment, git note, and Mandible API resolution record. |
| `open` | Reopen a closed issue |
| `description show` | Show only the issue description, without comments or metadata in human output. |
| `description edit` | Edit an issue description through the ledger body API, preserving issue-body revision history. |
| `description history` | Show read-only revision history for the issue description. This maps to Mandible's `issue_body` revision entity. |
| `work-notes show` | Show the current working notes without comments or metadata in human output. |
| `work-notes edit` | Replace working notes through the issue PATCH API, preserving immutable working-notes history. |
| `work-notes clear` | Clear working notes through the issue PATCH API, preserving the immutable clear event. |
| `work-notes history` | Show read-only working-notes revision history. |
| `kind set` | Set the canonical issue kind; labels remain independent presentation metadata. |
| `priority set` | Set the issue priority to `low`, `normal`, `high`, or `urgent`. |
| `comment add` | Add a comment to an issue. Compatibility alias: `mandible issue comment <issue-ref> -m <text>`. |
| `comment show` | Show one comment. Accepts a raw comment ID, `<issue-ref>#<ordinal>`, or `<issue-ref>#last`. |
| `comment history` | Show read-only text revision history for one comment. Accepts a raw comment ID, `<issue-ref>#<ordinal>`, or `<issue-ref>#last`. |
| `revision show` | Show one globally addressed text revision by revision ID. Revision IDs are unique across issue-description and comment revisions. |
| `revision diff` | Print a unified diff between two text revisions. Cross-entity diffs are rejected unless `--force` is passed. |
| `label add` | Add one free-form label; it does not change typed issue metadata. |
| `label rm` | Remove one free-form label; it does not change typed issue metadata. |

Prefer `mandible issue report <id> --json` when an agent needs issue context for a handoff or planning pass. Agents remain responsible for synthesis and decisions; the CLI output is only a deterministic fact packet.

Revision inspection commands are read-only. They expose stored snapshots and
derived diffs; they do not restore, edit, or roll back issue descriptions or
comments. Compatibility aliases `body-history` and `comment-history` are still
accepted but are not the preferred command names.

### mandible work-unit

Policy-free ledger mechanism client for worktree and commit wrappers. These
commands are Mandible-owned mechanism; worktree layout, branch naming, signing,
and attribution policy belong to callers such as dotfiles.

```
mandible work-unit claim --issue <id> --repo <repo> [--branch <branch>] [--parent-branch <branch>] [--kind solo|partition|integration] [--expected-generation N] [--parent-role-checkpoint C] [--session <id>] [--graceful]
mandible work-unit activate --issue <id> --repo <repo> [--branch <branch>] [--session <id>] [--worker] [--graceful]
mandible work-unit find --repo <repo> (--issue <id> | --branch <branch>) [--state open|committed|resolved|abandoned] [--graceful]
mandible work-unit resolve --id <work-unit-id> --expected-generation <n> [--auth-request-id <id>] [--graceful]
mandible work-unit release --repo <repo> --branch <branch> --expected-generation <n> [--graceful]
```

**Subcommands:**

| Command | Description |
|---|---|
| `claim` | Create or reuse a branch-based work unit using explicit issue/repo/branch/session inputs |
| `activate` | Mark the matching work unit committed, or auto-claim it in committed state |
| `find` | Find work units by repo plus issue or branch, with optional state filtering |
| `resolve` | Patch a work unit to resolved after a successful merge, optionally linking the auth request |
| `release` | Release active work units for an abandoned issue/repo lane |

### mandible auth list

List active auth requests from the Mandible daemon.

```
mandible auth list [options]
```

The active queue includes pending, approved, executing, expired, failed, and
recently resolved requests. Use this before submitting when a request may
already exist but the request ID is unknown.

**Options:**

| Flag | Description |
|---|---|
| `--json` | Print raw queue JSON after client-side filters |
| `--repo <name>` | Filter by repository name |
| `--head <branch>` | Filter by head/source branch |
| `--base <branch>` | Filter by base/target branch |
| `--status <status>` | Filter by request status |
| `--type <type>` | Filter by auth request type |

### mandible auth check

Check whether a branch can merge cleanly against the target branch and the
current pairwise-independent auth queue.

```
mandible auth check [--branch <branch>] [--repo <name>] [--target <branch>] [--cwd <path>] [--json]
```

The check is read-only: it verifies that no tracked worktree changes or
in-progress merge state would be disturbed, then uses Git's merge-tree
machinery without writing to the worktree. It reports target conflicts first,
then the queued request that makes the candidate conflict in queue order.

### mandible auth clearance

Issue, inspect, revoke, or consume a narrowly scoped protected-merge clearance.
Creation, reads, and revocation are operator-only; creation requires one fresh
hardware touch.
Execution succeeds only for the exact durable agent credential, canonical
project, protected base, merge request, issue and/or head scope, active runtime,
expiry, revocation state, and remaining use count recorded by the grant.

```bash
mandible auth clearance create --grantee <agent> [--request <request-id>] \
  [--project <project> --base <protected-branch>] [--credential <credential-id>] \
  [--issue <issue-ref>] [--head <branch>] \
  [--duration-minutes <n>] [--max-uses <n>] [--json]
mandible auth clearance list [--request <request-id>] [--json]
mandible auth clearance show <clearance-id> [--json]
mandible auth clearance revoke <clearance-id> [--json]
mandible auth clearance execute <request-id> [--json]
```

Creation is prospective; `--request` is optional provenance and scope prefill.
The defaults are one use and 60 minutes. Skill, prompt, session, and ambient
provider claims are never clearance authorization.

### mandible auth request

Submit an auth request and optionally watch for resolution.

```
mandible auth request <branch> --title <text> --issue <id> (--message <text> | --message-file <file>) --verification <text> [options]
```

**Required for a merge request:**

| Arg | Description |
|---|---|
| `<branch>` | Branch to merge into the protected branch |
| `--title <text>` | Dashboard title |
| `--issue <id>` or `--closes-issue <id>` | At least one issue (repeatable) |
| `--message <text>` | Agent-authored canonical change message (see below) |
| `--message-file <file>` | Alternative to `--message`: read the change message from a file (`-` for stdin) |
| `--verification <text>` | The checks run and their results; becomes the `Verification:` section |

**Options:**

| Flag | Description |
|---|---|
| `--type <type>` | Auth request type (default: `merge`). Options: `merge`, `commit`, `force-push`, `branch-delete`, `config-change`, `data-delete` |
| `--issue <id>` | Issue ID to reference for context; does not close on merge (repeatable) |
| `--ref-issue <id>` | Alias for `--issue` |
| `--closes-issue <id>` | Issue ID to close on successful merge (repeatable) |
| `--diff-summary <text>` | Override diff (auto-generated, truncated at 100KB) |
| `--spec <text>` | Inline spec/review Markdown |
| `--spec-file <file>` | Read spec/review Markdown from a file (`-` for stdin); mutually exclusive with `--spec` |
| `--handoff <text>` | Post-merge handoff note for next session |
| `--depends-on <id>` | Auth request ID that must complete first |
| `--repo <name>` | Override auto-detected repo name |
| `--cwd <path>` | Override auto-detected protected branch worktree path |
| `--target <branch>` | Override auto-detected target branch |
| `--timeout <seconds>` | SSE watch timeout (default: 14400 / 4 hours) |
| `--no-watch` | Submit only, do not poll for resolution |
| `--force` / `-f` | Skip CWD validation checks |

**Auto-detection:**

The script auto-detects:
- Protected branch (`develop` if it exists, otherwise `main`)
- Protected branch worktree path (from `git worktree list`)
- Repo name (from git common dir)

The daemon captures merge counts and the unified diff from the exact reviewed
commits. The CLI displays the returned counts rather than computing a second
set locally.

**Canonical change message:**

`--message` / `--message-file` supply prose only: the first non-empty line is
the outcome, and the rest is the body where the agent writes `Why:` and an
optional `Caveats:` section. The CLI owns the rest of the template — the
`Merge <branch>: ` subject prefix, the `Verification:` section from
`--verification`. Authoring the Verification heading
or a `#`-leading line is refused. Issue references and closure targets are
separate structured fields; commit messages have no operational semantics.

Every merge request, including a `--supersedes` replacement, must carry the
message and its verification text. The daemon refuses a merge request without
them and names the missing flag, so no client can submit one.

The daemon validates canonical formatting and the Verification section.
It then records the SHA-256 of the exact stored bytes
and freezes both once the request leaves `pending`. `mandible auth merge`
re-verifies that digest against the exact bytes it fetched, asserts they are
already canonical, and commits them on every merge path, aborting rather than
falling back. A request submitted before messages were required, and therefore
carrying none, still merges with git's own default merge message.

**Review specification:**

For a non-trivial merge, prefer `--spec-file` and author a readable Markdown
review packet. The CLI treats these bytes as opaque text: it does not parse,
reflow, canonicalize, or infer headings, and legacy one-line `--spec` values
remain valid unchanged. Use these sections:

- `Intent` — the requested outcome and its issue or coordination record are the
  source of truth.
- `Design choices` — the final committed implementation and durable design
  decisions are the source of truth.
- `Scope`, including `Non-goals` — the issue boundary and final diff are the
  source of truth.
- `Verification`, including limitations — executed checks and observed results
  are the source of truth; record gaps rather than predicting success.
- `Delivery` — repository policy and the actual activation plan are the source
  of truth. Mandible tracks going live itself through registered post-merge
  hooks and the request's convergence state, so the specification does not
  restate it. Record `operator-gate: none` unless a different gate truthfully
  applies.

The canonical change message and review specification stay separate because
they serve different contracts. The canonical message is concise, validated,
SHA-256-bound, frozen review input that becomes the merge commit message. The
specification is the detailed Markdown packet used to review intent, choices,
scope, evidence, and activation. Supplying `--spec-file` does not alter message
composition, verification-envelope ownership, digesting, freezing,
closure behavior, or stored spec semantics.

**Pre-flight checks:**

1. Validates CWD is on the protected branch
2. Validates the source branch exists
3. Verifies the branch has unique commits
4. Applies the explicit protected-root dirty policy without discarding files
5. Runs Mandible's shared auth check for tracked dirtiness and dry-run conflict detection

**Resolution watching:**

Unless `--no-watch` is specified, opens an authenticated POST stream at
`/api/events/subscribe` and waits for the matching `auth:resolved` event. It
falls back to one authenticated status read if that connection closes.

**Fallback on submission interruption:**

`mandible auth request` requires the daemon-owned preflight. If the daemon
becomes unreachable after preflight but before request submission completes,
the CLI can still print or spawn the equivalent `mandible auth merge` command
for manual recovery.

### mandible auth merge

Interactive merge command for protected branches. Requires user authentication via YubiKey.

When the approved request carries a canonical change message, the merge fetches
it, verifies its SHA-256, and uses those exact bytes as the merge commit message
on the `git merge` path, the atomic `git commit-tree` path, and a resumed
`git merge --continue`. A fetch failure, a missing message, or a digest mismatch
aborts before any ref or worktree changes.

```
mandible auth merge <source-branch>
mandible auth merge <source-branch> --into <target>
```

**Options:**

| Flag | Description |
|---|---|
| `--into <branch>` | Target branch (default: auto-detected protected branch) |

**Behavior:**

1. Strips agent git config overrides (merges use user's YubiKey, not agent key).
2. Detects and resumes in-progress merges (`MERGE_HEAD`).
3. Runs Mandible's shared auth check for tracked dirtiness and conflict detection.
4. Shows a summary box with diff stats for the source branch.
5. Prompts for confirmation (reads from `/dev/tty`).
6. Performs `git merge --no-ff --no-edit -S` (signed merge).
7. Auto-resolves conflicts in generated dist files (takes `--theirs`).
8. Verifies the merge is not empty (tree differs from parent).
9. Applies explicitly authorized structured issue closure actions.
10. Closes issues declared in the auth request's `issue_closures` field.
11. Cleans up merged branch worktrees through the configured worktree removal
    policy (`wt rm` in the reference dotfiles profile; `dwt` is a compatibility
    alias there).

Mandible's core merge preflight does not call user dotfiles scripts. Local
conventions such as worktree symlink hygiene belong in explicit policy hooks
or repo-local workflow configuration, separate from the merge-cleanliness
predicate.

### mandible search

Search conversation history across all providers.

```
mandible search "<query>" [options]
```

**Options:**

| Flag | Description |
|---|---|
| `--provider <name>` | Filter: `claude`, `gemini`, `codex`, or `all` (default: `all`) |
| `--role <role>` | Filter: `user` or `assistant` |
| `--since Nd` | Only conversations from last N days |
| `--limit N` | Max results (default: 20) |
| `--title` | Search conversation titles only (fast, no decompression) |

**Examples:**

```bash
mandible search "worktree merge"
mandible search "auth request" --provider claude --since 7d
mandible search "training loss" --role assistant --limit 5
mandible search "bigbuild" --title
```

Searches the SQLite database directly, decompressing gzip-compressed blocks via Python.

### mandible logs

Inspect provider-native source logs without importing, reconciling, or mutating the Mandible database.

```
mandible logs inventory [--provider codex|claude|gemini|all] [--since Nd|YYYY-MM-DD] [--limit N] [--json]
mandible logs capabilities [--provider codex|claude_code|gemini] [--json]
mandible logs missing [--provider codex|claude|gemini|all] [--json]
mandible logs orphans [--provider codex|claude|gemini|all] [--json]
mandible logs inspect <path|session-id> [--provider codex|claude|gemini|all] [--parse] [filters] [--json] [--head N]
```

Use `logs` commands when the provider files are the object of inspection. They treat Codex/Claude/Gemini source logs as the veridical transcript record and only compare against the DB index when needed.

| Command | Description |
|---|---|
| `inventory` | List recent provider source files, optionally with lightweight parsed metadata. |
| `capabilities` | Show the normalized roles, block types, tool metadata, source globs, and limitations emitted by each provider parser. |
| `missing` | List source files not represented in `conversations.source_path`. |
| `orphans` | List DB conversation rows whose `source_path` no longer exists. |
| `inspect` | Show source-log metadata and the first raw records for a path or provider session ID. With `--parse`, run the provider parser and return normalized blocks without mutating the DB. |

Parsed inspection filters:

| Flag | Description |
|---|---|
| `--role user|assistant|system|tool` | Match normalized block role |
| `--type TYPE[,TYPE...]` | Match normalized block type |
| `--tool NAME` | Match `metadata.tool_name` |
| `--tool-kind KIND` | Match provider-specific `metadata.tool_kind` when available |
| `--since TIME` / `--until TIME` | Match block timestamps. Bounds accept ISO timestamps, `YYYY-MM-DD`, and `Nd` for `--since`. |
| `--content TEXT` | Case-insensitive substring match against block content |
| `--limit N` | Limit results after filtering |

### mandible conversations

Inspect DB-backed normalized conversation rows and blocks.

```
mandible conversations list [--provider claude|codex|gemini|all] [--since Nd] [--limit N] [--json]
mandible conversations show <id|session-id> [--json] [--blocks]
mandible conversations blocks <id|session-id> [filters] [--json]
mandible conversations export <id|session-id> [--format json|markdown]
mandible conversations search "<query>" [search options...]
```

Use `conversations` commands for Mandible's normalized SQLite index, UI/export/search surface, and conversation metadata. `mandible conversations blocks` uses the same role/type/tool/time/content filters as `mandible logs inspect --parse`. `mandible conversations search` is an alias to `mandible search`.
