# Auth Queue

The auth queue is Mandible's mechanism for gating destructive or privileged operations behind user authentication. When an agent needs to perform an action that requires elevated trust — merging into a protected branch, force-pushing, deleting data — it submits an auth request. The request enters a queue visible in the dashboard, where the user reviews it and either approves (triggering execution with their signing key) or rejects it.

This decouples the agent's work from the moment of authentication. The agent submits and moves on; the user authenticates when they're ready.

## Auth Request Types

Every auth request carries a `type` field that describes what kind of operation is being requested. The queue supports six types:

| Type | Description |
|------|-------------|
| `merge` | Merge a feature/integration branch into the protected branch. This is by far the most common type. |
| `commit` | Create a signed commit on a protected branch (rare — most commits go on feature branches with the agent key). |
| `force-push` | Force-push to a branch. Destructive by nature, so it requires explicit approval. |
| `branch-delete` | Delete a branch. Used for cleanup after merges. |
| `config-change` | Modify a configuration that affects system behavior (e.g., Mandible settings, signing config). |
| `data-delete` | Delete stored data (conversations, sessions, etc.). Irreversible, so it's gated. |

The type defaults to `merge` if not specified, which maintains backward compatibility with older CLI versions.

## Request Lifecycle

An auth request moves through a well-defined state machine:

```
pending → executing → completed (exit_code 0 = success, non-zero = failure)
pending → needs_rebase (post-merge revalidation found a new conflict)
pending → rejected
pending → withdrawn (exact requester credential or session)
pending → superseded (one explicit atomic replacement)
pending → expired (TTL exceeded, default 24 hours)
completed (failed) → pending (via retry)
expired → pending (via retry)
needs_rebase → pending (via retry after rebasing or integration)
```

### Statuses

- **pending** — Waiting for the user to act. The request is visible in the dashboard queue.
- **executing** — The user approved and the command is running. Output streams to the dashboard in real time.
- **needs_rebase** — Another approved merge changed the target branch and this queued request now conflicts. Rebase or consolidate the branch, then retry the request.
- **completed** — Execution finished. Check `exit_code`: 0 means success, anything else is a failure. Completed requests are immutable history; a new attempt requires a new request.
- **rejected** — The user explicitly declined the request.
- **expired** — The request sat in `pending` for longer than the TTL (24 hours by default) without action. Expiry is checked every 30 seconds.
- **withdrawn** — The exact original requester withdrew a still-pending request with a reason.
- **superseded** — An explicit replacement atomically made this request inert, or a successful request proved an exact sibling obsolete.

Every transition appends an immutable revision containing the resulting request/action snapshot, its SHA-256 digest, the prior snapshot when applicable, actor evidence, reason, related request, and timestamp. Migrated historical rows receive an honest baseline snapshot without invented provenance.

## Submitting Requests

Requests are typically submitted via the `mandible auth request` CLI command, which carries authored messages, issue IDs and specs to the API. The daemon captures merge counts and the diff. When an agent needs to check whether a request already exists and does not know the request ID, it should run `mandible auth list --repo <repo> --head <branch> --base <branch>` first. When it needs to check whether a branch is independent from the queued merge work, it should run `mandible auth check --branch <branch> --repo <repo>`. The raw submission API endpoint is:

```
POST /api/auth/request
```

Required fields:
- `command` — The shell command to execute upon approval (e.g., `mandible auth merge feature/my-branch`).
- `title` — A human-readable description shown in the dashboard.

Key optional fields:
- `type` — One of the six auth request types. Defaults to `merge`.
- `session_id` — Links the request to the agent session that submitted it.
- `repo`, `base_branch`, `head_branch` — Branch metadata for merge requests.
- `diff_summary` — Unified diff content; merge submission replaces it with the server capture.
- `commit_message` — The proposed merge commit message. Its prose does not establish issue links or closure intent.
- `canonical_message` — Declares `commit_message` to be the agent-authored canonical change message. The daemon validates the machine-owned envelope (a `Verification:` section matching the `verification` field, no `#`-leading lines), canonicalizes the bytes, stores them back, and records the SHA-256 of those exact bytes in `commit_message_digest`; `mandible auth merge` then commits exactly those bytes. Both are immutable once the request leaves `pending`; an explicit `canonical_message: false` demotes the message back to free-form review text while still pending.
- `verification` — The `Verification:` section text. Required whenever `canonical_message` is true.
- `spec_content` — A specification explaining the intent and design decisions.
- `issue_references` — Issue IDs attached for review context/provenance; these do not close on merge.
- `issue_closures` — Issue IDs to close on successful merge.
- `issues` — Legacy close-on-merge issue list; prefer `issue_closures`.
- `depends_on_id` — Another auth request ID that must complete first (dependency chaining).
- `execution_mode` — `"daemon"` (default, Mandible executes locally) or `"remote"` (an external process manages execution).
- `supersedes_request_id` — Exact pending predecessor replaced in the same transaction. The requester, canonical project, and protected target must match.
- `superseded_action_dispositions` — One `{ordinal, reason}` entry for every predecessor action not carried with byte-equivalent semantics.

### Change breakdown

Merge requests show a **Change breakdown** panel beneath Specification in Info.
Language, directory, file-role, generated/vendor and largest-file views all use
one stored file inventory. Rows expose files, additions, deletions and share of
changed text lines, with contributing files available through expansion or
directory navigation. View choices persist per request.

Counts include comments and blank lines. Binary files show byte sizes instead
of line counts; submodule references are identified separately. Generated and
vendored files remain included, with independent flag groupings.

Classification uses versioned filename/path rules and committed
`linguist-language`, `linguist-generated` and `linguist-vendored` attributes.
Unknown formats remain Unknown. File-role precedence is fixtures/data, tests,
documentation, configuration, implementation, then other. These labels describe
rule-based categories, not inferred purpose or effort.

Reports and their bounded diff previews share pinned commit IDs and Git diff
rules. User configuration, private attributes and working-tree changes do not
affect capture. Historical requests without a report show Unavailable; they are
not recomputed from current branches. Collection failures and candidates over
10,000 changed files are explicit submission errors.

### Duplicate Detection

The queue automatically detects duplicate submissions. If an agent accidentally submits the same request twice, the API returns `409 Conflict` with the existing request's ID. A materially changed request must use explicit supersession; Mandible never infers replacement from branch or title similarity.

Duplicates are detected by two signals:
1. **Same branch pair** — If a pending/approved request already targets the same `head_branch` and `base_branch`, it's a duplicate regardless of which session submitted it.
2. **Same session + title** — If the same session already has a pending request with the same title.

### Pairwise Independence

For merge requests, Mandible runs the same read-only merge preflight used by
`mandible auth check` before queueing. The protected worktree must not have
tracked dirty state or an in-progress merge, and the candidate branch must
merge cleanly into the target branch. It must also remain clean after the
already queued merge requests for the same repo and target branch are simulated
in queue order. Independent branches may sit in the queue together. A
conflicting branch is rejected with a file-level clash report and should be
rebased or consolidated onto an integration branch.

### Mandible Issue Reference Verification

Merge requests use structured issue references and explicit issue-closure actions. Commit messages are not inspected for issue metadata.

## Reviewing and Acting on Requests

The dashboard and `mandible auth list` display the auth queue with all active requests. For each request, the user sees:

- Title and type
- Repository and branch information
- Diff summary (files changed, additions, deletions)
- The specification, if one was attached
- Linked issue IDs
- Dependency status (if the request depends on another)

### Available Actions

**Approve** (`POST /api/auth/request/:id/approve`) — Starts execution. The environment is sanitized so the operation uses your signing key (not the agent's). Output streams in real time via SSE.

**Reject** (`POST /api/auth/request/:id/reject`) — Declines the request with an optional reason. The result is delivered to the agent's inbox.

**Skip** (`POST /api/auth/request/:id/skip`) — Moves the request to the back of the queue without rejecting it. Useful when you want to approve a different request first.

**Withdraw** (`POST /api/auth/request/:id/withdraw`) — Lets the exact original requester withdraw its own pending request. A reason is required. API-token requests require the same credential; session requests require the same exact session.

**Retry** (`POST /api/auth/request/:id/retry`) — Resets a failed or expired request back to `pending` with a fresh TTL. The user can then approve it again.

Delete and dismiss are retired lifecycle operations. Their old endpoints return `410 Gone`; request rows and lifecycle receipts remain durable.

## Execution

When a request is approved, Mandible spawns the command in a sanitized environment. Agent signing overrides are stripped so the operation uses your signing key, and output streams to the dashboard in real time. Commands that don't complete within the timeout are terminated to prevent the queue from blocking.

### Execution Modes

Requests have an `execution_mode` field:

- **`daemon`** (default) — Mandible spawns and manages the command locally. This is the standard flow.
- **`remote`** — An external process manages execution. Mandible only tracks state transitions (pending, approved, completed). The external process reports output and results via the API. Used for operations that run on a different machine.

### Serialized Execution

Auth commands execute sequentially, not in parallel. Each command must complete before the next one starts. This prevents conflicts between concurrent merges and ensures the queue processes in a predictable order.

## Post-Execution Hooks

After a successful execution (exit code 0), Mandible runs any configured auth hooks before reporting the result. Hooks are configurable shell commands that run in the repository directory with metadata injected via environment variables.

See [Auth Hooks](#hooks) below for the full hook system.

## Hooks

Auth hooks are shell commands that run automatically after a successful auth operation. They replace what used to be hardcoded logic in the merge script (like "rebuild dist if source changed" or "restart the daemon if dist changed").

### Hook Properties

| Field | Description |
|-------|-------------|
| `repo_pattern` | A glob pattern matching repository names, or `*` for all repos. |
| `auth_type` | Which auth request type triggers this hook (e.g., `merge`, `commit`). |
| `command` | The shell command to execute. Runs via `bash -c`. |
| `label` | A human-readable description shown in the dashboard and execution output. |
| `enabled` | Whether the hook is active. Disabled hooks are skipped during execution. |
| `builtin` | System-seeded hooks that cannot be deleted (only disabled). |
| `position` | Execution order — lower values run first. |
| `required` | Whether this hook is part of convergence (default: true). A required hook that fails leaves the request `merged / convergence failed` and withholds its deferred issue closures. An advisory hook (`required: false`) is reported but never withholds anything. |

### Hook Environment

A hook is operator-registered but not operator-supervised at run time, so it
receives a **scrubbed allowlist environment**, never the daemon's ambient
`process.env`. Anything not listed here — API tokens, provider credentials,
`SSH_AUTH_SOCK`, `MANDIBLE_*` daemon configuration, shell customization — is
deliberately absent. A hook that needs more must resolve it from the repository
it runs in.

Inherited from the daemon when set: `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`,
`LC_CTYPE`, `TZ`.

Controlled by Mandible:

- `PATH` — `$HOME/.local/bin:$HOME/.cargo/bin:$HOME/bin` followed by a fixed
  system path. This includes the standard per-user Rustup/Cargo tool location
  without inheriting arbitrary daemon launcher paths. An inherited PATH would
  let whatever launched the daemon decide which `git`, `node`, or `npm` a
  protected-merge finalizer executes. Override with the `auth_hooks.path`
  setting.
- `TERM=dumb` and `CI=true` — a finalizer is non-interactive by construction.

Injected facts:

- `MANDIBLE_AUTH_REQUEST_ID` — The completed auth request's ID.
- `MANDIBLE_AUTH_TYPE` — The type of auth action (merge, commit, etc.).
- `MANDIBLE_AUTH_REPO` — The repository name.
- `MANDIBLE_AUTH_BRANCH` — The head branch.
- `MANDIBLE_AUTH_BASE_BRANCH` — The base (target) branch.
- `MANDIBLE_HOOK_ID` — The hook's ID.
- `MANDIBLE_HOOK_LABEL` — The hook's label.
- `MANDIBLE_HOOK_ATTEMPT` — 1-based attempt number for this execution.
- `MANDIBLE_HOOK_EXECUTION_ID` — The durable execution row's ID.
- `MANDIBLE_HOOK_COMMAND_DIGEST` — SHA-256 of the command bytes being run.

### Execution Behavior

- Hooks run **sequentially** in position order.
- Each hook has a **5-minute timeout** (SIGTERM, then SIGKILL after 5 seconds).
- Hook failures do **not** change the auth result and never block the queue.
  The merge already succeeded; a hook failure never authorizes rerunning it.
- Hook output is streamed to the same SSE channel as the main execution, prefixed with `[hook: <label>]`.

### Convergence

Merged is not the same as live. Execution state for each (auth request, hook)
pair is persisted in `auth_hook_executions` **before** the process is spawned,
so a daemon that dies between the merge and hook completion leaves a durable
record instead of losing convergence. Each row snapshots the hook ID and the
exact command bytes plus their SHA-256 digest at the moment execution begins, so
a retry reruns those bytes and a later edit to the hook definition is visible
rather than silently substituted.

Execution is at-least-once with a bounded budget of 3 attempts per pair. A
resumed sweep (daemon startup, and the idle tick) reruns runnable rows. **A
retry reruns the hook command only — never the merge.**

Auth requests therefore report one of three states alongside `completed`:

| Convergence | Meaning |
|---|---|
| `complete` | Merged, and every registered hook succeeded. |
| `pending` | Merged, but a hook has not finished. The machine is not live yet. |
| `failed` | Merged, but a required hook exhausted its attempts. Merged, not live. |

A required-hook failure:

- leaves the merge successful and the queue unblocked;
- **withholds deferred issue closures** until convergence completes;
- notifies the originating session (`auth:convergence` SSE event) and creates
  exactly one deduplicated inbox alert keyed by (request, hook);
- preserves the hook output and full attempt history on the request;
- does **not** create a ledger issue. An issue is for a repairable defect, not
  for every transient host failure.

`POST /api/auth/request/:id/retry-convergence` grants one more attempt and
reruns the snapshotted hook command.

### Managing Hooks

Registering a hook registers a command that Mandible executes unsupervised on
the operator's machine after a protected merge. Reading the registry is ordinary
state; mutating it is an authority grant, so **create, update, and delete
require the `change_settings` global capability** (`GET` stays open). Reviewed
protected bytes plus a prior hook registration jointly authorize execution —
neither alone is sufficient, and a repository cannot opt itself into execution
by containing an executable file.

Hooks are managed via the API:

- `GET /api/auth/hooks` — List all hooks.
- `POST /api/auth/hooks` — Create a new hook. Requires `change_settings`.
- `PUT /api/auth/hooks/:id` — Update a hook. Requires `change_settings`.
- `DELETE /api/auth/hooks/:id` — Delete a hook. Requires `change_settings`; fails for built-in hooks (disable them instead).

## Dependency Chains

Auth requests can declare a dependency on another request via `depends_on_id`. The dashboard shows the dependency status alongside the request, so the user knows which requests need to be approved first.

Dependencies are informational — Mandible does not enforce ordering automatically. The user is responsible for approving requests in the correct order. However, the dashboard surfaces dependency status so this is straightforward in practice.

## Proven sibling supersession on success

When a merge request completes successfully, Mandible marks only proven same-project, same-target, same-head siblings `superseded` and links them to the successful request. It also revalidates the remaining pending merge requests for the repo against the new target head. Requests that now conflict move to `needs_rebase`, broadcast an auth result, and appear in the submitting session's inbox.

## Work Unit Resolution

On successful merge, the queue automatically resolves associated work units --- those linked to the request directly, those on the merged branch, and those linked to explicit closure issues.

After resolution, Mandible archives reliably linked terminal Codex worker threads for the closed child issues. The archive target is the Codex provider thread ID from the console session; live parent-role holders, active Mandible sessions, and running console sessions are skipped.

This closes the loop between the auth queue, the issue tracker, and the work-unit lifecycle.

## Stuck Request Recovery

Mandible automatically recovers requests that get stuck due to daemon crashes or other interruptions. On startup, it examines incomplete requests and determines whether they actually succeeded (by checking for merge evidence in the output) or should be marked as failed. During runtime, a periodic check catches requests that have been stuck too long and marks them as interrupted.

This ensures the queue never gets permanently stuck, even after unclean daemon restarts.

## Result Delivery

After an auth request resolves (completed, rejected, withdrawn, superseded, expired), the result is broadcast via SSE (`auth:resolved` event) and delivered to the submitting agent's inbox. The next time the agent starts a session, the session-start hook picks up inbox items and surfaces the result.

## SSE Events

The auth queue broadcasts these SSE event types:

| Event | When |
|-------|------|
| `auth:new` | A new request is submitted or a failed request is retried. |
| `auth:updated` | Request metadata is modified (title, diff, spec, etc.). |
| `auth:output` | Execution output chunk (stdout/stderr). |
| `auth:resolved` | Request reached a terminal state (completed, rejected, withdrawn, superseded, expired). |
| `auth:lifecycle` | An immutable lifecycle revision was appended. |
