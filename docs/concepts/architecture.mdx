# Architecture and system concepts

Mandible is a local agent operations manager for one operating-system user. It
organizes issues, work, reviews, approvals, artifacts, and conversations across
projects and agent sessions. The daemon serves a browser application and local
clients; the desktop application presents the same system. Opening Mandible
always gives the local user access, without login, pairing, or an expiring
session.

## Authorship, responsibility, and permission

These are independent questions, not levels in a hierarchy:

- **Authorship and provenance** record who created or changed a record and what
  evidence identifies the actor. They remain part of its history when work is
  handed off. Local agent calls carry a provider/session or managed app/session
  claim; this identifies an actor but is not human approval.
- **Responsibility** identifies the user and session currently accountable for a
  work unit, umbrella parent role, or request. Assignment and process bindings
  describe execution separately. Ordinary writes do not silently take over:
  an authorized agent explicitly assumes responsibility with a reason and the
  observed generation or checkpoint. This may happen even if the holder is live
  or its liveness is unknown. Handoff and relinquishment preserve work state;
  stale writers fail. A transfer does not stop a running process or grant human
  approval.
- **Permission for protected effects** comes from the configured operator's
  fresh key proof, bound to the action, installation, and relevant context.
  Merge approval binds the exact candidate and reviewed request. Ordinary project
  work such as sharing, review text, and annotations remains attributed without
  treating that attribution as operator proof. Proposal disposition requires
  human proof; promotion staged on an approved merge uses that approval's exact
  binding.

The local CLI uses an owner-only Unix socket. Local bearer tokens do not confer
responsibility or operator authority; unknown or conflicting managed identities
are refused. Remote and scoped transports retain their credential boundaries.
See [Local client access](/docs/local-client-access),
[Work units](/docs/concepts/work-units), and
[Approvals](/docs/features/auth-queue).

## Where information lives

Provider-native files own conversation transcript bytes. Mandible's canonical
ledger stores conversation and session identities, annotations, relationships,
source bindings, and Mandible-authored operational records. These include issue
and comment text, approval requests, and durable chat-control outbox messages;
the ledger is not a mirror of provider conversation history. Navigation and
masked search indexes are disposable. Sparse position anchors identify places in
conversations; provider-native anchors support native resume.

A metadata backup can be restored into a new database. Normal discovery,
ingestion, and reconciliation reconnect available native sources and rebuild
derived indexes. A metadata backup does not promise to contain transcripts or
reconstruct a missing provider session: unavailable content stays unavailable.
See [Conversations](/docs/features/conversations) and
[Conversation recovery](/docs/conversation-recovery).

Operational logs live separately in `operational-logs.db`. Artifacts have their
own custody: a version points either to tracked Git content or bytes retained by
Mandible. The SQLite ledger uses migrations applied at startup.

## Interfaces

The daemon serves the application and API over the local HTTPS front door, with
Server-Sent Events for updates and WebSockets for terminal I/O. The CLI uses the
local socket by default. Agent sessions may be managed or external; provider
integration determines available process controls and event data, not a rank
or a different authorship or approval model. See
[Agent integration](/docs/concepts/agent-tiers) and
[Real-time events](/docs/concepts/real-time-events).
