# Approvals: End to End

The Approvals view holds reviewed operations. The `auth` CLI namespace, API routes,
and stored identifiers stay stable. Merge requests prepare their Git context and
reviewed merge command; other request types require an explicit command and execution
context. Submission never runs the operation, including when the daemon is unavailable.

```bash
mandible auth request --type config-change \
  --command './apply-reviewed-settings.sh' --cwd /absolute/project \
  --repo example --title 'Apply reviewed settings' --issue <id> --no-watch
```

Non-merge requests share submission, approval, output, and history with merges. Their
type is a review category, not a command generator. Dedicated operation-specific
builders for commits, force-pushes, branch deletion, configuration changes, and data
deletion are not supplied. Merge-only flags are refused on this path, and `--command`
cannot override a merge request. Existing approval and execution permissions still apply.


This guide walks through the complete lifecycle of an authenticated operation, from the moment an agent finishes work on a feature branch to the result being delivered back to the agent's inbox.

## 1. Agent Completes Work on a Feature Branch

The agent has been working in a feature branch worktree — say `feature/add-dark-mode`. It has made commits using the agent signing key, with the work unit linked to its tracking issue in the ledger. The work is done, tests pass, and the agent is ready to merge into the protected branch.

At this point, the agent cannot merge directly. The protected branch requires user authentication (a YubiKey signature). If the agent needs to check whether a request already exists and does not know the request ID, it first runs `mandible auth list --repo <repo> --head <branch> --base <branch>`. If other requests are already queued for the repo, it can run `mandible auth check --branch <branch> --repo <repo>` to confirm pairwise independence before submitting. Then it submits an auth request.

## 2. Submitting the Auth Request

The agent runs:

```bash
mandible auth request feature/add-dark-mode \
  --title "Merge feature/add-dark-mode: dark mode support" \
  --closes-issue abc1234 \
  --message-file ./change-message.md \
  --verification "Unit and UI suites pass; dark mode checked in the dashboard." \
  --no-watch
```

For merges, the `mandible auth request` CLI automatically detects the protected branch and repository, computes diff stats, runs Mandible's read-only merge preflight, checks for duplicate requests, and submits everything to the Mandible API. Use `--issue` for reference-only issue context and `--closes-issue` only for issues the merge should close. To replace reviewed bytes, pass `--supersedes <request>` and carry every staged action identically or dispose it with repeatable `--drop-superseded-action <ordinal>:<reason>`.

The `--no-watch` flag is standard — it means the CLI exits after submission rather than watching for the result via SSE. Auth results are delivered asynchronously via the inbox.

`change-message.md` holds the agent-authored change message: an outcome line,
then a short `Why:` paragraph, and an optional `Caveats:` section for any
post-merge manual step. The CLI adds the merge subject prefix and the
`Verification:` section. Requests carry no separate spec; a substantial design
belongs in a tracked document registered as an artifact and linked to the
issue.

### Protected-Root Dirty Policy

Before submitting a merge, `mandible auth request` checks the protected-branch worktree.
It never restores, checks out, cleans, or otherwise discards dirty files. The
default policy is `block`: tracked, staged, or untracked dirtiness causes the
request to fail with the exact file list.

Override one request explicitly with:

```bash
mandible auth request feature/add-dark-mode \
  --title "Merge feature/add-dark-mode: dark mode support" \
  --issue abc1234 \
  --dirty-policy branch-off \
  --no-watch
```

Repos can set their default in `mandible.toml` or `.mandible.toml`:

```toml
[auth.protected_root_dirty]
default_policy = "block"
allow_untracked = false
branch_prefix = "shelve/protected-root"
include_untracked = true
```

Supported policies:

| Policy | Behavior |
| --- | --- |
| `block` | Fail without modifying the protected root. |
| `allow-untracked` | Continue only when all dirtiness is untracked files. |
| `stash` | Preserve dirty state as a stash commit under `refs/mandible/protected-root-dirty/`, outside the stash stack every worktree shares, then continue. Restore it with `git stash apply --index <sha>`. |
| `branch-off` | Move dirty state to a `shelve/protected-root-*` branch and worktree, then continue. |

When `allow-untracked`, `stash`, or `branch-off` lets a submission continue, the
CLI prints the stash, branch, and worktree details and sends the action with the
request. Mandible stores it on the request as `protected_root_dirty_action`,
and the approval page shows it read-only under
**Protected-root changes**, so the reviewer can see where uncommitted work went.

After the explicit dirty policy is resolved, request submission and approved
merge execution both use the same Mandible auth check for tracked dirty state
and merge-tree conflict prediction. User-specific worktree hygiene, such as
symlink repair, should be configured as an explicit policy hook rather than as
part of the core merge predicate.

### What Gets Submitted

The API receives a payload roughly like:

```json
{
  "command": "mandible auth merge feature/add-dark-mode",
  "title": "Merge feature/add-dark-mode: dark mode support",
  "type": "merge",
  "repo": "my-app",
  "base_branch": "main",
  "head_branch": "feature/add-dark-mode",
  "cwd": "/path/to/repo",
  "files_changed": 12,
  "additions": 340,
  "deletions": 45,
  "diff_summary": "src/theme.ts | 120 ++++...\nsrc/settings.tsx | 85 +++...",
  "commit_message": "Merge feature/add-dark-mode: dark mode support\n\nWhy:\nAdds a dark mode toggle to the settings panel...\n\nVerification:\nUnit and UI suites pass.",
  "canonical_message": true,
  "verification": "Unit and UI suites pass.",
  "issues": ["abc1234"],
  "session_id": "sess-xyz",
  "execution_mode": "daemon"
}
```

The request enters the queue with status `pending`.

## 3. Request Appears in the Dashboard

The Mandible dashboard shows the auth queue with all pending requests. The new request appears with:

- The title and type (merge).
- Repository and branch names.
- A diff summary showing what changed.
- The specification explaining the intent.
- Linked issue IDs.
- A timestamp and expiry countdown (24 hours from submission).

The dashboard receives the `auth:new` SSE event in real time, so it updates instantly.

## 4. User Reviews the Request

The user examines the request in the dashboard. They can see:

- **Diff stats** — How many files changed, lines added/deleted. A quick sanity check.
- **Diff summary** — The git stat output showing which files were touched.
- **Commit message** — The canonical change message: the outcome, why it matters, any post-merge caveats, and the verification run. This is the primary review surface.
- **Linked issues** — Click through to the issue details for full context.
- **Dependency status** — If this request depends on another (e.g., a prerequisite merge), the status of that dependency is shown.

If something looks wrong, the user can:
- **Update the request** (`PUT /api/auth/request/:id`) to correct metadata before approving.
- **Reject it** with a reason that gets delivered to the agent.
- **Skip it** to review other requests first.
- **Dismiss it** to remove it from the queue entirely.

## 5. User Approves

The user clicks Approve. This triggers `POST /api/auth/request/:id/approve`.

Mandible signs a fresh challenge with the configured operator key and verifies it against active registered operator credentials. The challenge includes the exact request and staged-action snapshot, a nonce, and a 60-second expiry. The request stays `pending` until verification succeeds. Cancel signing, a missing key, an expired challenge, or changed reviewed bytes leave it unexecuted. The dashboard offers **Cancel signing** while proof is pending.

After verification, the request transitions to `executing`. Ordinary local browsing requires no proof or login.

## 6. Execution

Mandible spawns the merge command as a child process. The execution environment is carefully prepared:

### Environment Sanitization

The daemon strips agent signing overrides from the environment before running the merge command. This ensures the merge uses your signing key (YubiKey) rather than the agent's software key.

### YubiKey Authentication

A hardware-backed operator key requires its physical signing interaction. Approval evidence records a verified credential signature; a click is never recorded as hardware presence.

Every protected merge creates and verifies a signed commit from the exact reviewed tree and parents before changing the protected ref, index, files, or merge state. Publication advances the ref with an expected-old-value check, then synchronizes the checkout without overwriting untracked collisions. Native preparation hooks are refused before signing when isolated candidate preparation cannot preserve their semantics. Native post-commit and post-merge hooks join the durable convergence plan with their executable digest and original arguments. Changed hook bytes or a later protected checkout fail visibly instead of replaying an old native hook on new files. Direct protected-checkout signing and interrupted `git merge --continue` are unsupported.

A successful result requires the exact publication receipt, authorized operator signature, reviewed candidate tree and parents, and reviewed canonical message. A zero exit code alone cannot close issues, promote Briefings, or run hooks. Applied publication state remains available for recovery; receipt recovery and post-publication effects never repeat the merge.

### Output Streaming

As the merge command runs, its stdout and stderr are captured and broadcast via SSE (`auth:output` events). The dashboard shows a live terminal-like view:

```
Executing merge command...
Merge made by the 'ort' strategy.
 src/theme.ts     | 120 ++++++++++++++++++++++++++++++++++++++++++++++++
 src/settings.tsx |  85 ++++++++++++++++++++++++++++++++++
 ...
 12 files changed, 340 insertions(+), 45 deletions(-)
```

### Timeout

If the merge doesn't complete within 10 minutes (e.g., the YubiKey isn't connected, git hangs on a network operation), the process is killed with SIGTERM, followed by SIGKILL after 5 seconds. The request is marked as failed.

## 7. Post-Merge Hooks

After a successful merge (exit code 0), Mandible runs any configured auth hooks. For example, a repository might have hooks that:

- Rebuild dist files if source changed.
- Restart the Mandible daemon if its own dist changed.
- Push to a remote.
- Notify a CI system.

Hooks run sequentially. Their output is streamed to the same SSE channel, prefixed with `[hook: <label>]`:

```
[hook: rebuild-dist] Building dist...
[hook: rebuild-dist] ok (2340ms)
[hook: restart-daemon] Restarting mandible daemon...
[hook: restart-daemon] ok (890ms)
```

Hook failures are logged but don't change the auth result — the merge already succeeded.

## 8. Result Recording

The command's exit code is stored. For a successful merge:
- Status becomes `completed` with `exit_code: 0`.
- `resolved_at` is set.

The auth queue broadcasts an `auth:resolved` SSE event.

### Auto-Dismiss Duplicates

Other requests are marked `superseded` only when Mandible can prove they identify the same canonical project, protected target, and reviewed head. The successful request is recorded as the explicit relationship target.

### Work Unit Resolution

Mandible resolves associated work units:
1. Any work unit with `auth_request_id` matching this request.
2. Any work unit whose `branch` matches `feature/add-dark-mode`.
3. Any work unit linked to issue `abc1234` through structured ledger records.

This closes the loop between the auth queue, the issue tracker, and the work-unit lifecycle.

## 9. Result Delivery

The result is delivered to the agent via two channels:

### SSE (Real-Time)

The `auth:resolved` event is broadcast immediately. Any dashboard client or SSE listener connected at that moment receives it.

### Inbox (Asynchronous)

The result is placed in the Mandible inbox for the session that submitted the request. The next time the agent starts a session, the session-start hook calls `mandible inbox` and picks up the result:

```
Auth request completed: Merge feature/add-dark-mode: dark mode support
Status: success (exit_code 0)
```

This asynchronous delivery model means the agent doesn't need to be running when the merge happens. It can submit the request and shut down. The result will be waiting when it comes back.

## What If Something Goes Wrong?

### Merge Conflict

If the merge has conflicts, the command exits with a non-zero code. The request is marked `failed` with the non-zero `exit_code`, its `failure_reason` summarizes the cause, and the error output shows the conflict details. If another approved merge invalidates a still-pending request before approval, Mandible moves that request to `needs_rebase` and delivers the result to the submitting session's inbox. The user or agent can:
- Have the agent resolve conflicts on the feature branch.
- Retry the request after resolution.

### YubiKey Not Present

Operator challenge signing has a 60-second limit and can be cancelled. Missing or unavailable credentials leave the request pending. Signed candidate failure leaves the protected checkout unchanged. A request with retained prepared publication state requires receipt recovery or operator inspection; retry cannot erase that state and repeat publication.

### Daemon Crash During Execution

If the Mandible daemon is killed mid-execution (e.g., by its own post-merge hook restarting it), the request gets stuck in `executing` status. On the next startup, Mandible's recovery logic examines the output to determine whether the merge actually succeeded, and marks the request accordingly. During normal runtime, a periodic check catches any requests that remain stuck and recovers them.

### Request Expires

If nobody acts on a request for 24 hours, it expires automatically. The agent receives an expiry notification in its inbox. It can resubmit if the work is still relevant.

## Checking Status Manually

If you need to check on a request outside the dashboard:

```bash
# By request ID
curl -s http://localhost:19420/api/auth/request/<id>

# List the active queue
mandible auth list

# Raw API fallback for the active queue
curl -s http://localhost:19420/api/auth/queue

# List resolved history
curl -s http://localhost:19420/api/auth/history?limit=10
```

The queue endpoint returns pending, approved, executing, needs-rebase, expired, failed, withdrawn, superseded, and recently resolved requests — everything the user might need to act on.
