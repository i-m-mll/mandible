# Canonical local origin migration

The production browser origin is declared once in `config/canonical-origin.json` as `https://mandible.localhost`. `node scripts/generate-canonical-origin.mjs --check` verifies the generated server, desktop, capability, browser, and CLI constants. The daemon stays on loopback HTTP port `29420`; the ordinary Caddy gateway listens on loopback HTTPS port `19420`. A separately installed macOS Packet Filter rule forwards loopback TCP port `443` to Caddy. This keeps the daemon and Caddy unprivileged. Preview origins remain on their isolated `19421` listener.

## Candidate verification before protected approval

Use a disposable `MANDIBLE_HOME` with its own installation authority, certificate, session database, and copied ledger for implementation and browser checks. Do not point candidate commands at the production home. Build the server, UI, and packaged desktop from the exact integrated candidate revision. Verify the generated origin check, Caddyfile adaptation, the old-host state page, strict host and Origin rejection, and origin registration compare-and-swap. **Before submitting protected approval**, launch the production daemon and packaged desktop together from that exact candidate revision, probe startup and one representative interaction, and inspect their logs for crash loops, repeated-event storms, database errors, and event-loop stalls. An isolated test harness can exercise the browser state contract. Exact `443` connectivity requires the operator to install the reviewed Packet Filter rule before auth on a test host or the approved production Mac. Record that operator action as a pre-auth gate. Do not stage the production registration in advance; the registered rebuild hook owns that deterministic merge transition.

## Protected cutover

The parent coordinator owns the operator gate before auth and browser acceptance after the protected merge:

1. Record `node scripts/local-origin-migration.mjs inspect`, the exact production installation ID, current registered origin, active Caddy configuration, daemon backend, browser profiles to preserve, and a rollback copy of service configuration. Confirm the installation-owned local CA is trusted and the generated origin files match the manifest. Check that no unrelated service or Packet Filter rule owns loopback port `443`.
2. Before auth, have the operator review `config/loopback-443.pf`, `config/bio.mll.mandible-loopback443.plist`, `scripts/loopback-443-activate.sh`, and `scripts/loopback-443-operator.sh`, then run `sudo sh scripts/loopback-443-operator.sh install` on the approved Mac. This installs one root-owned child anchor under the existing `com.apple/*` redirect anchor and a LaunchDaemon that restores it at boot. The helper acquires one PF enable token and stores it in `/var/run`; it does not reload the main ruleset or edit `/etc/pf.conf`. Existing files with different bytes stop installation. The installer waits for the exact two live rules before succeeding; independently check IPv4 and IPv6 `443` connectivity. Do not run Caddy or the Mandible daemon as root.
3. The required `builtin-mandible-rebuild` hook builds the merged candidate, installs the desktop app, marks the protected build ready, and runs `local-origin-migration.mjs converge-hook` when the canonical manifest was added by this merge. The hook validates the completed old-origin cutover, installation identity, protected commit, trusted CA, and gateway custody. It journals the previous Caddyfile, changes only `instance_registrations.public_origin` under compare-and-swap, configures the bounded old-host recovery page, and reloads the existing gateway. An interrupted hook retries the staged journal; a reload failure fails convergence and preserves the prior Caddyfile in the journal for recovery. The existing self-merge restart then starts the protected runner with the new origin and temporary migration mode. Installation ID, instance ID, role, permissions, effect ceiling, writable roots, session families, and actor provenance stay in their existing custody.
4. The normal production site uses forwarded port `443`. The old `https://app.mandible.localhost:19420` site serves only the saved-state export page; the gateway accepts only its exact origin on the bounded recovery ingress, strips credentials, and forwards no old-host application routes. Inspect the new daemon and Caddy health after self-merge restart; hook success alone does not prove live delivery.
5. Launch the packaged desktop app and verify native bootstrap, the host-only cookie on `mandible.localhost`, health readiness at `https://mandible.localhost/api/health`, CLI access, preview isolation, and one representative protected interaction. Open each old browser profile at its old URL, including profiles whose session has expired, and move its saved workspace. Confirm its intended route, selections, drafts, and view settings at the new origin. An expired or revoked old cookie is never migration proof; connection must follow the installed-app access contract. Check the daemon and desktop logs for restart loops, repeated events, database errors, and stalls.
6. After every required browser profile has restored its state, remove `MANDIBLE_ORIGIN_MIGRATION=allow`, restart the daemon, run `npm run local-front-door -- configure`, and reload the same gateway. Verify the temporary old page is inaccessible and the new origin remains ready. Then run `node scripts/local-origin-migration.mjs complete --confirm-browser-conversion`. Completion refuses an unready final origin or a configured old-host migration route.

## Interruption and rollback

Before completion, stop the exact daemon and gateway and run `node scripts/local-origin-migration.mjs rollback`. It changes only the registered origin back to the journaled value under compare-and-swap and, for a hook-staged migration, restores the exact journaled Caddyfile only if the current file is the expected temporary migration configuration. Any unrelated gateway drift stops rollback for review. Restore the prior daemon and desktop service configuration. After proving the old origin is healthy, the operator runs `sudo sh scripts/loopback-443-operator.sh remove`. Removal first checks that all installed files still match the reviewed bytes, then unloads only this LaunchDaemon and child anchor, releases its own PF enable token, and removes only its three files. The main PF ruleset and other anchors remain untouched. The journal and the old browser's local storage remain available for inspection. Do not delete the session authority or installation-owned certificate to recover a failed cutover.

After a browser profile has written state to the new hostname, the old hostname cannot read that new origin's storage or host-only cookie. Prefer forward recovery from the journal and preserved old storage. A completed migration has no automatic rollback command; reversing it would require a new guarded migration and a fresh browser-state plan.
