# Local browser sessions

Mandible browser access uses one durable installation authority and one opaque, host-only cookie per browser environment. Renderer code never receives the reusable session credential. CLI and file-RPC clients continue to use explicit bearer or capability credentials, but browser requests cannot fall back to them.

## One-time setup

1. Run `npm run local-front-door -- initialize`. This explicit, idempotent step establishes the installation authority before any daemon can create browser sessions.
2. Start the production daemon on its loopback backend (port `29420`).
3. Run `npm run local-front-door -- install`. This downloads Caddy `2.11.3` for the current macOS architecture and verifies the release SHA-256 pinned in `scripts/pinned-caddy.mjs`.
4. Choose **Connections → Set up secure local connections…** in the macOS desktop app, or run `node scripts/local-ca-trust.mjs setup` from an operator terminal. This explicit action uses a temporary loopback-only Caddy listener, not ports `19420` or `19421`, to create the installation's root in persistent storage. If macOS does not already trust that exact root, the action explains the computer-wide change and asks for OS approval. It verifies a connection signed by the pinned root and one using macOS trust before recording success. A denial leaves a resumable prepared receipt, not a replacement root or silent retry.
5. Start the ordinary front door with `npm run local-front-door -- run`. Its Caddyfile keeps `skip_install_trust`; previews, restarts, and routine certificate renewal do not request another system trust change.

The root certificate and signing-key digests are pinned to the installation authority in `~/.mandible/config/local-sessions/ca-trust.json`; Caddy's storage stays at `~/.mandible/config/local-sessions/caddy-storage/`. Changed or missing root, key, installation identity, or gateway storage fails visibly. `node scripts/local-ca-trust.mjs status` inspects that custody without changing trust. Manual Keychain installation is a troubleshooting path only, not the normal setup. Certificate trust makes the HTTPS origin usable; browser pairing below is a separate authorization step.

The registered production origin is `https://app.mandible.localhost:19420`. The Caddy admin API and every backend listener remain loopback-only. Redirects and ambient proxy discovery are disabled for native enrollment.

## Pair a browser once

An unpaired browser displays a short reference. Approve that exact reference from an authenticated operator terminal:

```sh
mandible user pair <reference>
```

Return to the browser and choose **Complete pairing**. The pairing secret is held only in a short-lived HttpOnly cookie. Approval creates a new independent session family; it never evicts another environment to make room.

Log out revokes only the current family. “Log out everywhere” revokes every family for that user. If the daemon is unavailable during logout, the browser records a revocation-pending marker and refuses further authenticated use until it can submit the revocation.

## Preview isolation

The preview launcher preserves public port `19421`, but gives each preview a distinct registered `.mandible.localhost` hostname and an unprivileged loopback backend port. It copies and sanitizes the ledger, registers the preview's exact origin, generation, effect ceiling, and writable roots, then reloads the front door.

Preview requests are authorized by the production authority and forwarded with a signed five-second installation context. Cookies and bearer credentials are stripped before the preview backend. The standard preview ceiling permits only ledger reads, writes to the copied ledger, and files beneath the registered preview root. Protected auth, production/shared files, external processes, provider sends, network publication, background delivery, and shared maintenance fail closed even for the operator.

## Migration and rollback

Migration is an explicit, temporary phase owned by `npm run local-session-cutover`. Author one `mandible-local-session-cutover@1` manifest with exact stable health facts for the old production and preview listeners, their typed lifecycle controls, durable credential directories, candidate backend processes, gateway commands, rollback files, and the intended preview metadata/database promotion. `prepare` binds each health check to the process actually listening on its public port, proves the candidate ports are free, captures exact file and registration rollback custody, and writes the journal before its compare-and-swap registration stage. A launchd-supervised production service must also prove that the exact loaded service owns the health-verified listener and record its domain, label, plist bytes and digest, loaded state, and enabled state. `activate --confirm-ca-trusted` writes intent before disabling and booting out that service, proves both supervisor absence and port 19420 release, then starts candidate backends and the gateway. The unmanaged preview listener uses its exact PID-bound stop control. Re-entry reconciles the observed supervisor, process, listener, and health state before completing or repeating an effect. An ordinary failure compensates to the captured legacy lifecycle; an interruption leaves a deterministic journal that `activate` or `rollback` can reconcile.

Migration mode serves the new UI at the exact old HTTP origins and exposes only the one-time HTTPS cookie ingress; it deliberately does not bind the final production or preview origins. A browser at an old origin can then exchange its protected legacy session once. Mandible keeps the old view state in the durable conversion transaction, installs the new host-only cookie at the migration ingress, restores that state after the final origin opens, and only then tombstones the legacy fingerprint and removes its exact file entry. Retries return the same replacement family, and a restored legacy file cannot resurrect a completed conversion.

After every browser has converted, run `npm run local-session-cutover -- complete --confirm-browser-conversion`. The operator confirmation first persists the forward-only `normal_pending` boundary, then the command restarts both candidate backends without legacy acceptance, reconciles or restarts a lost gateway before normal reload, and promotes the typed preview metadata plus `current.db` target. Completion records the legacy production service suspended while the gateway owns port 19420. Interrupted completion resumes forward from its pending intents and never silently returns to migration or legacy acceptance. The normal configuration omits both migration listeners, and the daemon rejects the old-origin exception. New previews derive a restricted child family automatically from the active production browser family through a one-time top-level transfer; the production cookie is never sent to the preview host. Revoking the production family also revokes all of its derived preview families. There is no compatibility mode or bearer fallback.

Before the operator-confirmed `normal_pending` boundary, `npm run local-session-cutover -- rollback` reconciles pending stops and starts, stops discovered candidate and gateway processes only when their identities match the journal, and restores files and registrations through separate exact custody records. An unmanaged old listener is started only if actually stopped. A supervised production service restores its captured enabled and loaded state through launchd, never by running its binary directly. After bootout, rollback verifies that the restored healthy listener belongs to that exact service and has a new startup epoch; after disable without bootout, it merely restores the enabled state. Plist drift or unexpected ownership fails visibly. Interrupted `rolling_back` work is resumable. Do not re-enable the deleted fragment, localStorage, anonymous SSE, WebSocket-subprotocol, or global-fetch credential paths piecemeal. Preserve `~/.mandible/config/local-sessions/` while investigating so session and registration custody remains auditable.

The manifest is operational authority and must contain no raw secret. Each legacy health expectation pins the pre-cutover release's actual health fields: startup epoch, commit, role, and database; the listener/process and supervisor binding supply the remaining authority proof. Production `legacy.lifecycle` uses `{ "kind": "launchd", "domain": "gui/501", "label": "com.mll.mandible", "plist_path": "/absolute/path/to/com.mll.mandible.plist" }` and has no direct `restore` command. Preview `legacy.lifecycle` uses `unmanaged` and retains its pinned restore command. Candidate `process.env` pins instance and installation identity, public origin, backend generation, `MANDIBLE_PORT`, allowed effects, writable roots, and the exact legacy `MANDIBLE_CLIENT_AUTH_DIR`. Candidate ports must be distinct loopback backend ports other than 19420 and 19421. `gateway.configure` supplies separate `migration_args` and `normal_args`; `gateway.process` starts the pinned Caddy process; `gateway.reload` reloads its private admin endpoint. Every command is an absolute executable plus an argument array. `preview_promotion` supplies launcher metadata for the candidate backend, its registered HTTPS origin on public port 19421, and the exact `current.db` target. Its metadata, `current.db`, and generated gateway configuration paths all appear in `rollback_files` with any other generated runtime file whose exact bytes must be restored.
