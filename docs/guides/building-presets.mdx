# Building Presets

This guide walks through creating, importing, editing, composing, and exporting presets step by step. By the end, you'll have a working preset system that shapes how agents behave in your projects.

## Creating a Preset from Scratch

### Via the API

The simplest way to create a preset is with a name and Markdown content:

```bash
curl -X POST http://localhost:19420/api/presets \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "My Project Conventions",
    "description": "Coding standards for the widget project",
    "content": "# Build\n\nAlways run `npm test` before committing.\n\n## Linting\n\nUse ESLint with the project config. Never disable rules inline without a comment explaining why."
  }'
```

Mandible parses the Markdown into a node tree:

```
Root
├── Build (level 1)
│   body: "Always run `npm test` before committing."
│   └── Linting (level 2)
│       body: "Use ESLint with the project config. Never disable rules inline without a comment explaining why."
```

The heading hierarchy determines the tree structure. Content between headings becomes the body of the preceding heading's node.

### Via Markdown Import

If you have conventions written in a Markdown file, you can import them with front-matter:

```bash
curl -X POST http://localhost:19420/api/presets/import \
  -H 'Content-Type: application/json' \
  -d '{
    "markdown": "---\nname: Widget Standards\ndescription: Coding standards for the widget project\n---\n\n# Build\n\nAlways run `npm test` before committing.\n\n## Linting\n\nUse ESLint with the project config."
  }'
```

The front-matter block (`---` delimited YAML at the top) sets the preset's name and description. Everything after the front-matter is parsed into nodes.

## Importing from CLAUDE.md

If you already have conventions in `CLAUDE.md` files (global or project-level), you can import them directly.

### Import Your Global CLAUDE.md

```bash
curl -X POST http://localhost:19420/api/presets/import-claudemd \
  -H 'Content-Type: application/json' \
  -d '{ "source": "global" }'
```

This reads `~/.claude/CLAUDE.md` and creates a preset named "Global CLAUDE.md" with source type `claude_md_global`.

### Import a Project's CLAUDE.md

```bash
curl -X POST http://localhost:19420/api/presets/import-claudemd \
  -H 'Content-Type: application/json' \
  -d '{ "source": "project", "cwd": "/path/to/my-project" }'
```

This looks for `/path/to/my-project/.claude/CLAUDE.md` first, then `/path/to/my-project/CLAUDE.md`. The preset is named after the project directory (e.g., "my-project CLAUDE.md") with source type `claude_md_project`.

### What Happens During Import

1. The Markdown is read from the file.
2. It's parsed into a node tree following heading hierarchy.
3. Headings inside fenced code blocks are correctly ignored.
4. Content before the first heading becomes a synthetic root node (level 0).
5. The content hash (SHA-256) is computed for deduplication.
6. All nodes are scanned for convention-setting links (see [Linking Conventions to Settings](#linking-conventions-to-settings) below).

## Editing a Preset

### Editing Individual Nodes

Add a new convention under an existing section:

```bash
curl -X POST http://localhost:19420/api/presets/<preset-id>/nodes \
  -H 'Content-Type: application/json' \
  -d '{
    "parent_id": "<parent-node-id>",
    "title": "Type Safety",
    "body": "Use strict TypeScript. Never use `any` — use `unknown` and narrow with type guards.",
    "level": 2,
    "position": 5
  }'
```

Update an existing node:

```bash
curl -X PUT http://localhost:19420/api/presets/<preset-id>/nodes/<node-id> \
  -H 'Content-Type: application/json' \
  -d '{
    "body": "Use strict TypeScript. Never use `any` — use `unknown` and narrow with type guards. Exception: third-party library interop where types are incomplete."
  }'
```

Move a node to a different parent or position:

```bash
curl -X PATCH http://localhost:19420/api/presets/<preset-id>/nodes/reorder \
  -H 'Content-Type: application/json' \
  -d '{
    "nodeId": "<node-id>",
    "newParentId": "<new-parent-id>",
    "newPosition": 3
  }'
```

Delete a node and all its children:

```bash
curl -X DELETE http://localhost:19420/api/presets/<preset-id>/nodes/<node-id>
```

### Bulk Replace from Markdown

If you've edited the Markdown externally (in your editor, in a PR), you can replace the entire node tree:

```bash
curl -X PUT http://localhost:19420/api/presets/<preset-id>/nodes \
  -H 'Content-Type: application/json' \
  -d '{
    "markdown": "# Build\n\nRun tests first.\n\n## Linting\n\nUse ESLint.\n\n# Deploy\n\nAlways deploy to staging before production."
  }'
```

This atomically deletes all existing nodes and re-creates them from the new Markdown. The preset's version number increments and the content hash updates.

## Composing Presets for a Session

The real power of presets is composition. A single agent session can draw conventions from multiple presets — your global conventions, project-specific rules, and task-specific guidelines — composed into one coherent system prompt.

### Attaching Presets to a Console Session

When creating a console session, pass preset IDs:

```bash
curl -X POST http://localhost:19420/api/console/sessions \
  -H 'Content-Type: application/json' \
  -d '{
    "label": "Feature work",
    "command": "claude",
    "backend_type": "sdk",
    "presetIds": ["<global-preset-id>", "<project-preset-id>"]
  }'
```

Or attach presets to an existing session:

```bash
curl -X POST http://localhost:19420/api/console/sessions/<session-id>/presets \
  -H 'Content-Type: application/json' \
  -d '{
    "presetIds": ["<preset-id>"]
  }'
```

Remove a preset from a session:

```bash
curl -X DELETE http://localhost:19420/api/console/sessions/<session-id>/presets/<preset-id>
```

### How Composition Works

When the SDK backend starts processing a prompt, it computes the union of all attached presets:

1. Presets are loaded in position order.
2. Each preset's node tree is serialized back to Markdown.
3. If two presets have identical content (same SHA-256 hash), the duplicate is dropped. This handles the case where you import the same CLAUDE.md into two presets.
4. The surviving Markdown chunks are joined with `---` separators.
5. The combined text becomes the system prompt for the Claude API call.

### Viewing the Computed Union

```bash
curl http://localhost:19420/api/presets/union?session_id=<session-id>
```

Returns:

```json
{
  "text": "# Hard Constraints\n\nNever merge directly...\n\n---\n\n# Build\n\nAlways run tests...",
  "tokenEstimate": 2847
}
```

The `tokenEstimate` is a rough count (`text.length / 3.5`) so you can check whether your composed conventions fit within the model's context window.

### Checking for Composition Warnings

Before starting a session with specific presets, validate that all required settings are configured:

```bash
curl -X POST http://localhost:19420/api/presets/validate-preset-ids \
  -H 'Content-Type: application/json' \
  -d '{ "presetIds": ["<id1>", "<id2>"] }'
```

If any preset convention has a `requires` link to a setting that's not configured, the response includes warnings:

```json
{
  "valid": false,
  "warnings": [
    {
      "conventionTitle": "Commit Signing",
      "settingKey": "commit_signing",
      "message": "Convention \"Commit Signing\" requires setting \"commit_signing\" to be configured."
    }
  ]
}
```

## Linking Conventions to Settings

Convention-setting links connect your rules to the system configuration that enables them. This lets you answer questions like "which conventions depend on commit signing being enabled?" or "what happens if I turn off the reaper?"

### Automatic Detection

When you create or update nodes, Mandible scans the text for known patterns and creates `references` links automatically. For example, a node mentioning "YubiKey" or "gpg-sign" gets linked to the `commit_signing` setting.

You don't need to do anything for auto-detection — it happens on every node write and bulk import.

### Creating Manual Links

For conventions that reference settings not covered by auto-detection:

```bash
curl -X POST http://localhost:19420/api/presets/nodes/<node-id>/links \
  -H 'Content-Type: application/json' \
  -d '{
    "settingKey": "my_custom_setting",
    "linkType": "requires"
  }'
```

Link types:
- `references` — The convention mentions this setting (informational).
- `requires` — The convention needs this setting to be active to be meaningful. Session validation checks these.
- `configures` — The convention describes how to configure this setting.

### Finding Conventions for a Setting

```bash
curl http://localhost:19420/api/presets/links?setting_key=commit_signing
```

Returns all conventions linked to that setting, with the node title, preset name, and link type. Useful when you're about to change a setting and want to understand which conventions depend on it.

## Working with Preset Diffs

Preset diffs are proposed changes to conventions. They typically come from agents that detect workflow violations or discover new patterns that should be codified.

### Viewing Diffs for a Session

```bash
curl http://localhost:19420/api/presets/diffs?session_id=<session-id>
```

### Reviewing a Diff

Each diff has a status: `proposed`, `accepted`, `rejected`, or `promoted`. When reviewing:

```bash
# Accept a diff
curl -X PUT http://localhost:19420/api/presets/diffs/<diff-id> \
  -H 'Content-Type: application/json' \
  -d '{ "status": "accepted" }'

# Reject a diff
curl -X PUT http://localhost:19420/api/presets/diffs/<diff-id> \
  -H 'Content-Type: application/json' \
  -d '{ "status": "rejected" }'
```

Accepting a diff is an acknowledgment — you still need to apply the change to the preset's node tree manually (edit or add the node). The diff system tracks the proposal lifecycle, not the application.

### Promoting Diffs

When a convention should move from a project preset to the global preset, change its status to `promoted`. Since this affects all projects, promoting a convention requires an auth request of type `preset-promote` — it goes through the same review-and-approve flow as a merge.

## Exporting Presets

Export a preset as Markdown with YAML front-matter:

```bash
curl http://localhost:19420/api/presets/<preset-id>/export
```

Returns:

```json
{
  "markdown": "---\nname: My Conventions\nversion: 3\nsource: manual\ndescription: Project standards\n---\n\n# Build\n\nAlways run tests.\n\n## Linting\n\nUse ESLint."
}
```

This format is portable — save it to a file and re-import it on another Mandible instance with `POST /api/presets/import`.

## Browsing the Convention Library

The convention library indexes all leaf-level conventions across all your presets:

```bash
curl "http://localhost:19420/api/presets/library?q=commit&limit=20"
```

Each result includes a breadcrumb showing the convention's location in its preset hierarchy. This is useful for discovering conventions you've written across different presets without remembering which preset they belong to.

## Practical Patterns

### Layer Your Conventions

A common setup is three layers:

1. **Global preset** — Imported from `~/.claude/CLAUDE.md`. Universal rules that apply everywhere: commit signing, branch protection, attribution requirements.
2. **Project preset** — Imported from `<repo>/CLAUDE.md`. Project-specific build commands, architecture decisions, testing conventions.
3. **Task preset** — Created manually for a specific class of work (e.g., "ML experiment conventions", "documentation writing conventions").

Attach all three to a session. The union engine composes them in order and deduplicates shared content.

### Keep Presets Focused

Each preset should have a clear scope. Don't put project build commands in the global preset. Don't put universal ethics rules in a project preset. The composition system is designed to let you separate concerns and recombine them as needed.

### Use Token Estimation

Before attaching presets, check the token estimate. If your composed conventions exceed 10-15% of the model's context window, consider trimming. The convention library can help identify redundant or low-value conventions across your presets.

### Validate Before Starting Sessions

Get in the habit of running validation before starting important sessions. Missing a required setting (like commit signing) can cause confusing failures mid-session that are obvious in hindsight but time-consuming to debug in the moment.
