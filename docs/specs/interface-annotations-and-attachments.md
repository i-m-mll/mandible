# Interface annotations and attachments

The contract for annotating Mandible's own interface and for the attachments a Chat message carries. Three parts: the Chat attachment flow and the Agentation toolbar, which are delivered and stay as described; and interface notes, which keep a toolbar note from the moment it is saved and file it onto an issue for later work. The shared code contract for interface notes is `src/interface-notes/contract.ts`; this document explains it and does not restate its types.

## Chat attachments

The Chat composer accepts text/code files and PNG/JPEG/WebP/GIF images through a plus control at the left of the bottom controls row, through file drops anywhere in the conversation detail pane, and through annotation staging from the toolbar. PDFs, office documents, archives, audio/video and arbitrary binaries are rejected with a concise actionable error. Attachments show above the text box in one non-wrapping horizontal row: a pill with a type icon, a truncated label, a full-name tooltip and a separate remove control. Clicking a pill opens a bounded preview modal: text, image, or the annotation's text and element context. Drafts and their attachments are browser-local (`ui/src/chat/attachmentDrafts.ts`) until submitted; order and draft ownership survive navigation and restarts; attachment-only messages are valid; failed or uncertain submission retains the exact draft intent and a retry never duplicates attachments or messages.

Delivery (`src/conversation-control/attachment-delivery.ts`): file contents never enter model context; the agent gets the filename and a retained readable path and decides what to read. Images and annotation screenshots use each provider's native image input. Annotation text and concise element metadata are inserted into message context as text, in the one form `annotationAttachmentText` produces. Bytes live in Mandible custody (`POST /api/chat-attachments`, `GET /api/chat-attachments/:id/content`, `chat_attachment_files`), with explicit size and count bounds and the local operator access model.

One discriminated contract, `ChatAttachment` in `src/conversation-control/attachments.ts`, covers drafting, submission, persistence (`conversation_control_outbox.attachments_json`), provider delivery, preview, and now interface notes.

## Agentation toolbar

Mandible mounts the bundled Agentation 3.1.2 toolbar (`ui/src/annotation/`). A navbar control above Settings shows or hides it; the preference survives refresh. Selection, popovers, markers, Copy, Clear, Settings and keyboard shortcuts are the package's own. The custom Mandible annotator from the comparison is excluded from delivery; its remaining store functions and the comparison document's claims about shared routes are removed with [issue:0c7ad7a].

Facts about the package that bound the design, read from its source (`dist/index.mjs.map`) and confirmed in the running app:

- Notes are kept in `localStorage` under `feedback-annotations-<pathname>`, one set per URL path. `loadAnnotations` drops a note whose `timestamp` is older than seven days and keeps a note without one. Since Mandible routes by path, every view and entity page has its own set.
- A mounted toolbar reads its page's set only in the effect keyed on the pathname, which runs at mount and whenever the pathname it reads at render changes. It writes its own state back to that key on every change. Nothing else makes it re-read storage: no prop, no imperative handle, no storage-event listener.
- Pins are drawn only while the toolbar is expanded (`isActive`), and the expanded flag lives in the outermost component, so a keyed remount collapses the toolbar to its launcher.
- Pins are placed from the stored `x` (percent of window width) and `y` (document pixels) without finding the element again.
- `onAnnotationAdd`, `onAnnotationUpdate`, `onAnnotationDelete` and `onAnnotationsClear` fire for the user's actions in the toolbar only. Clear also fires for the automatic clear after Copy or Send when the user's `autoClearAfterCopy` setting is on.
- Send is shown when `onSubmit` is given and enabled only when the current page has at least one note. It awaits `onSubmit`, shows a sending state and disables itself while the promise is pending, then shows a sent or failed state for 2.5 seconds; a throw or rejection is the failed state. The callback receives the current page's notes.
- A note's id is `Date.now().toString()`; its editor refuses an empty comment.
- The toolbar does not support adding buttons, a fixed page key for the whole app, or forcing a clear after Send. No fork or patch of the package.

## Interface notes

### Terms

A note is one annotation made with the toolbar on Mandible's interface or on another app's page (see Other apps): its app, its text, the element context of the shared attachment contract (`AnnotationTarget`, including the build revision of the page it was made on), and Agentation's own pin record. A note has one owner: none (unfiled) or one issue comment (filed). A page is a URL path of the app. The loaded issue is the one issue, if any, whose filed notes are currently shown as pins.

### Behaviour

**Notes are kept when made.** Adding, editing or deleting a note in the toolbar writes to the daemon at once. Unfiled notes reappear in every browser that opens the same instance, do not expire, and each pin is shown on the page where its note was made. A write that fails leaves the note in the toolbar and is retried at the next reconciliation; the rail control shows that writes are pending.

**Send.** The toolbar's Send opens one Mandible menu, which names how many unfiled notes it acts on (every page's, not only the current page's) and lists the destinations:

- the loaded issue, first and preselected, when there is one;
- New issue, which opens a title field prefilled with the first note's text; Enter files, Escape returns to the list;
- the open issues of the receiving project that carry notes, most recently annotated first;
- the selected writable Chat, which stages the notes on that draft as attachments and leaves them unfiled.

Choosing an issue files the notes as one new comment on it. Filing moves notes: a filed note is never copied to a second issue, and filed pins leave the toolbar. Dismissing the menu files nothing and settles Send in its failed state, which is the package's only way to show that nothing was sent. Without a receiving project the menu offers Chat only.

**The rail control.** The navbar Agentation control keeps its click (show or hide the toolbar). It shows the number of unfiled notes in the app, and its hover tip names the loaded issue. Its context menu is the same menu Send opens, so notes can be filed from a page that has none, and the loaded issue can be unloaded there.

**Issues.** An issue that carries notes is an ordinary issue: no special kind, no label, the ordinary open and closed lifecycle. An issue created from Send has kind `unknown` until an agent sets it, the given title, and an empty body; its notes are comment 1. The receiving project is the instance setting `interface_notes_project`, chosen on the Settings view from the registered projects.

A comment that carries notes shows them in the issue view as the pills Chat uses, each opening the same preview; its body text is not shown there, because it is the text form of the same notes. The remove control on a pill removes the note from the comment, and removing the last note soft-deletes the comment. The preview of a filed note has a pin action that loads the issue and opens the note's page.

**Agents.** The body of a comment that carries notes is the one text form Chat delivery gives an agent, `Annotation n: <text>` followed by the labelled context fields, one block per note, regenerated by the daemon on every change to the comment's notes. So `mandible issue show`, `mandible issue report`, issue search, the Markdown export and every other consumer of comment bodies show the notes without change, and a hand edit of such a body is refused. `mandible issue triage --notes` lists only issues that carry notes, most recently annotated first; the Send menu uses the same query.

**Loading an issue's notes.** The issue's header menu has Show pins, which loads the issue, opens the page of its first note, and shows and expands the toolbar there (the package draws pins only while it is expanded), and Hide pins while it is loaded. One issue is loaded at a time; loading another replaces it. The loaded issue is browser view state and survives refresh. A loaded pin looks like any other pin; its hover card shows the note's text. While an issue is loaded:

- editing a loaded note's text edits the note on the issue, and the comment body's revision history records it;
- deleting a loaded pin, or Clear, removes it from the toolbar only; the issue is unchanged and the pin returns when the issue is loaded again;
- Send files only unfiled notes, with the loaded issue preselected.

### Mechanism

**Authority and cache.** The daemon holds every note. Agentation's local storage is a cache Mandible fills, one key per page, with the Agentation pin record of each note that belongs on that page (unfiled notes and the loaded issue's notes), its `comment` set from the note's text and its `timestamp` omitted. The toolbar reads a page's cache when it mounts and when the user navigates to the page, so a cache written while the user is elsewhere shows up without further action.

Reconciliation is one routine, run at boot before the toolbar mounts, after filing, on load and unload of an issue, and on the `interface_note:changed` event: fetch the unfiled notes and the loaded issue's notes, write every page's cache, remove cache keys for pages that have none, and remount the toolbar (a React `key` on the host) only when the current page's set changed by something other than this toolbar's own actions. The remount collapses the toolbar to its launcher; after filing that is the natural end of the action. Show pins expands it again through `revealToolbarPins`, which presses the launcher found by its accessible name `Start feedback mode` in the toolbar's shadow root; in the remaining cases the user expands it. Changes made in another browser to a page the user is not on need no remount.

The toolbar's own writes to the cache (its state after each user action) and the daemon's record agree because every toolbar action is also a daemon write:

| toolbar callback | unfiled note | loaded (filed) note |
| --- | --- | --- |
| `onAnnotationAdd` | `POST /api/interface-notes` with id, text, target (from the existing adapter mapping, `revision` = `servedBackendGeneration()`), pin | not applicable |
| `onAnnotationUpdate` | `PATCH /api/interface-notes/:id {text}` | the same; the server revises the comment body |
| `onAnnotationDelete` | `DELETE /api/interface-notes/:id` | nothing |
| `onAnnotationsClear` | `DELETE` each unfiled note in the batch; notes the host has just filed are skipped | nothing |

Which column applies is the host's last knowledge of the note, and another browser may have filed it since. The daemon therefore decides the dangerous case: the plain `DELETE` deletes only an unfiled note and answers 409 `note_filed` otherwise, leaving the comment untouched; removing a filed note from its comment is a different call, `DELETE /api/interface-notes/:id?comment=<comment_id>`, which only the issue view makes. An edit needs no such guard: changing a note's text is what the user asked for whoever owns the note. When a response shows an owner the host did not expect (`note_filed`, or a patched note that comes back filed), the host reconciles.

Refusals are `{ error: <code>, message? }` with the codes and statuses of `INTERFACE_NOTE_ERRORS`; the browser surface throws `InterfaceNotesApiError { status, code }`. A failed write is recorded in browser storage as pending and replayed at the next reconciliation. A replay is done when it succeeds or when the daemon already holds, or has moved past, the state it asked for: `note_exists` on a create, `note_not_found` or `note_filed` on an edit or delete (`interfaceNoteWriteSettled`). Any other failure keeps it pending. Notes present in the toolbar's cache before this design (the user's existing notes) are uploaded once, at the first reconciliation on that browser, and a flag records that this migration ran; no other cache content is ever uploaded, so a note deleted elsewhere is never resurrected from a stale cache.

**Storage.** One table, in `src/db-baseline.ts` and a migration, classified for backup like `chat_attachment_files`:

```sql
CREATE TABLE interface_notes (
  id TEXT PRIMARY KEY,
  comment_id TEXT REFERENCES ledger_comments(id) ON DELETE CASCADE,
  text TEXT NOT NULL,
  target_json TEXT NOT NULL,
  pin_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  app TEXT NOT NULL DEFAULT 'mandible',
  origin TEXT
);
CREATE INDEX idx_interface_notes_comment ON interface_notes(comment_id);
```

`comment_id NULL` is unfiled. `app` is the app the note was made on and `origin` the embedding page's origin, null for Mandible's own (migration 244 added both, and `interface_note_embed_grants`, which migration 245 keyed by app; earlier notes are Mandible's). Validation of text and target reuses the annotation validation now in `ChatAttachmentStore.resolve`, extracted so both callers share it; `pin_json` must be a JSON object whose `id` equals the row id. Notes within a comment are ordered by `created_at`; a note's ordinal is its 1-based position there, computed at read time. Revision history for filed notes is the comment body's: every regeneration is a `comment_body` revision with reason `edit` through the existing body-revision path. No new entity type and no new revision table. Full-text search covers notes because the body is indexed already.

**Comments that carry notes.** Filing runs in one transaction: resolve or create the issue, create the comment with body `renderInterfaceNotesBody(notes)` through the store's `addComment` (operator attribution from the request, source `mandible`), set `comment_id` on the listed notes that are still unfiled, and emit `ledger:comment:created` plus `interface_note:changed`. Text edits and removals of filed notes regenerate the body the same way; removing the last note soft-deletes the comment (`LedgerStore.softDeleteComment`): `deleted_at` is set, the references its body made are withdrawn, links that target it are cleared, `ledger:comment:deleted` is emitted, its ordinal is never reused, and a deleted comment can no longer be edited. The ledger store announces its events after the outermost transaction commits, so a store write composed into the filing transaction never announces a rollback. Filing creates nothing when every listed note was filed or deleted meanwhile, and answers 409 `nothing_to_file`. `PATCH /api/ledger/comments/:id` with a `body` for a comment that carries notes returns 409 `comment_body_generated`.

**API.** Routes, payloads and the setting key are in `src/interface-notes/contract.ts`; browser calls go through `ui/src/annotation/interfaceNotesApi.ts`. The routes declare `ledger:read` or `ledger:write`, except in a preview that keeps notes in its source (below). Every write requires the operator: notes are the user's own evidence, so an agent reads them (the list route and every comment body are open to any authenticated identity) and never makes, edits, files or removes them. `GET /api/interface-notes` lists the unfiled notes of one app, `?app=<key>`, Mandible's by default; a create names its app, Mandible's when absent, and another app's create names its page's origin (see Other apps). `new_issue` on filing may name a `project`, which receives the new issue instead of `interface_notes_project`. `GET /api/issues?has_notes=true` filters each repo's issues to those that carry notes, adds `interface_notes: { count, last_at }` to each (a field on `GitBugIssue` in `src/types.ts`, present only on this query), and orders them by `last_at` descending; `cli/issue.sh` passes the query for `triage --notes`. The issue detail projection (`src/issue-detail-contract.ts`) gains `notes: InterfaceNote[]` on `LedgerIssueDetailComment` and on the comment timeline entry, in comment order. New issues created by filing go through the store's `createIssue` with kind `unknown`; the route is reachable only by the operator's browser identity, and the existing rule that an agent must give a concrete kind is untouched.

**Events.** `interface_note:changed` is added to the event allowlist in `src/contracts.ts` with the payload in the contract file. The payload names the app whose unfiled notes changed, or null when any may have (a filing's comment, a relay's reconnection, an event from a source of an earlier build); a host reconciles for its own app or null. The UI's per-event cache switch invalidates the issue detail and issue list caches for it as it does for `ledger:` events.

**Previews.** A note made in a preview instance has the same standing as one made in the instance the preview was copied from, and is kept there; the note's `target.url` (the preview origin) and `target.revision` (the preview's build) record where and on which build it was made. The effect `notes:source` ("write interface notes to the instance this preview was copied from") is in a preview's effect ceiling exactly when its `source_db_path` is the live ledger (`resolvesToProductionDbPath`); `effectsForInstance` in `src/security/effect-policy.ts` computes the ceiling, and the launcher (`scripts/iab-preview.mjs`) requests and checks that same set. A preview copied from any other database, such as a fixture, lacks the effect and keeps notes in its copy like every other ledger write.

With the effect (`keepsNotesInSource`), every interface-notes route declares `notes:source` instead of `ledger:*`, applies its own requester check (any identity for the list, the operator for writes) in the preview, and then sends the request's method, matched path, query and body, without agent markers, to the source's local socket (`productionLocalApiSocketPath`), which attributes it to its operator; the source's answer is returned as is (`src/interface-notes/source.ts`). So the preview's toolbar shows and edits the source's unfiled notes, and filing from a preview creates the comment on the source. When the source does not answer, the route returns 503 `source_unavailable`, which the toolbar keeps pending and replays. The preview subscribes to the source's `interface_note:changed` events over the same socket and re-emits each one to its own clients, plus one event with no ids on each (re)connection, since changes made while it was disconnected were not seen; it reconnects after a second when the stream ends. Nothing else a preview does reaches the source: no other route declares `notes:source`. The preview's own copy still answers everything else, so an issue's comments and the issues offered by Send (`has_notes`) are those of the copy, and filing to an issue that exists only in the copy answers `issue_not_found`.

The production instance carries `notes:source` in its ceiling too, though no production route declares it, because the browser context a preview receives is signed by production with the intersection of the preview's ceiling and production's. An installation registers its production ceiling once and starts production with the registered ceiling, so the registration is brought up to the current default when the installed build is updated or started (`reconcileMainRegistration` in `scripts/local-runtime.mjs`, for any registered ceiling that is an earlier default). A preview of a build with `notes:source` whose production instance does not hold the effect yet answers 403 `effect_forbidden` to the browser on every interface-notes route; the toolbar keeps those writes pending in that origin's storage and replays them once the routes answer.

**Settings.** `interface_notes_project` is an ordinary row in `settings`, read and written through the existing `GET /api/settings` and `PUT /api/settings/:key`. The Settings view shows it as a row with a `NativeSelect` over `listCanonicalProjects()`, with an empty choice.

**UI composition.** The pieces, and who may depend on what:

- `ui/src/components/shared/AttachmentPill.tsx`: `AttachmentPillRow` (the non-wrapping row inside `OverflowFade`) and `AttachmentPill({ attachment: ChatAttachment; highlighted?: boolean; onOpen(): void; onRemove?(): void; removeDisabled?: boolean })`, which derives its label (`Annotation n`, or the file name), icon and tooltip from the attachment. `AttachmentPreviewModal({ attachment: ChatAttachment | null; onClose(); actions?: JSX.Element })` wraps `DetailPaneModal` and renders `AnnotationPreviewContent` or the image or text preview. These replace the inline JSX and `conv-compose__attachment*` rules in `ui/src/views/conversations.tsx` and `ui/src/styles/conversations.css`; the classes move to `attachment-pill*` in their own stylesheet. The Chat composer and the issue comment card both use them; the comment card hides its body when the entry has notes and passes `interfaceNoteAttachment(note, ordinal)`.
- `ui/src/annotation/notesTransport.ts`: `InterfaceNotesTransport`, every call the store and menu make to the daemon. `interfaceNotesApi.ts` implements it over this origin's API for one app (`apiTransport`); `embedClient.ts` implements it over the bridge.
- `ui/src/annotation/interfaceNotesStore.ts`: the browser's one authority for one app's notes, configured once with `configureInterfaceNotes({ app, transport, revision, migrateLegacyCache, storageScope })` (`mandibleNotes.tsx` for Mandible's interface, `embed.tsx` for the embed). It exposes a snapshot `{ ready, unfiled: InterfaceNote[], loadedIssue: { id, notes } | null, pendingWrites: number, epoch }` with `subscribe`, and the actions `reconcile()`, `setLoadedIssue(issueId | null)`, `recordAdd/Update/Delete/Clear` for the toolbar callbacks, and `markFiled(ids)`. The loaded issue is persisted with `usePersistedViewState`'s helpers under `mandible.agentation.loadedIssue:v1`; pending writes and the migration flag under `mandible.agentation.pending:v1` and `mandible.agentation.migrated:v1`. In the embed both keys end in `:<app>`, since the page's origin may serve several apps over time, and the legacy migration does not run.
- `ui/src/annotation/AgentationHost.tsx` replaces `AgentationPreview.tsx`: mounts `<Agentation key={epoch} appName={appName} ...callbacks onSubmit>` once the store is ready; `onSubmit` opens the menu and returns a promise the menu settles.
- `ui/src/annotation/InterfaceNotesMenu.tsx`: the Send menu, built on `useAnchoredMenu` and `app-anchored-menu`, anchored to the control that opened it: the toolbar's Send button, found by its accessible name `Send Annotations` inside the open shadow root of the `agentation-toolbar` element (stable for the pinned package), or the rail control. It takes `ports: { transport, receivingProject, Notice, chat?, issueTitle? }` and is otherwise independent of Mandible's interface; Mandible passes `mandibleNotesMenuPorts`, whose `chat` stages to Chat through `chatDestination.ts`; the embed passes no `chat`, so its menu has no Chat destination. It files through the transport, then calls `markFiled` and `reconcile()`. `useAnchoredMenu` takes the event's composed path and the root node's active element, so the menu works inside the embed's shadow root.
- `ui/src/annotation/AgentationToggleButton.tsx` gains the count, the hover tip and the context menu.
- `ui/src/annotation/toolbarView.ts`: whether the toolbar is shown (browser view state under `mandible.agentation.visible:v1`, read by the app and set by the rail control) and `revealToolbarPins()`.
- Issue view: the header menu items Show pins and Hide pins, and the preview's pin action, consider only Mandible's notes, since another app's page is not Mandible's to open; they call `setLoadedIssue`; Show pins and the preview's pin action then navigate with `navigateTo` to the note's page and call `revealToolbarPins()`.

**Chat destination.** Staging to Chat takes the same set the menu names, in page then creation order, as `interfaceNoteAttachment` attachments, with the existing duplicate and 16-attachment checks of the adapter; the notes stay unfiled.

### Other apps

**Behaviour.** A development server of a registered project, running on this machine, can show the same toolbar and Send menu on its own pages by loading one script from the daemon: `<script type="module" src="<daemon origin>/embed/notes.js">`, added by the app's own dev tooling (Feedbax's Vite plugin, for example). The first time a page's origin asks, it shows only a small link, Allow Mandible notes, which opens Mandible's Settings view as its own page with that origin's request marked; once the operator allows it there, the page shows the toolbar. Its notes are the app's own: its unfiled notes appear only on its pages, Send files them onto a new issue of the app's project or onto the project's open issues that carry notes, and the filed comment is an ordinary comment that carries notes, shown in Mandible's issue view like any other. Its menu has no Chat destination and no loaded issue. A page whose origin serves no registered project, and a page where the daemon does not answer, show nothing.

**App.** A note's app is `mandible` for Mandible's own interface, or `<project key>:<path within its checkout>` for another app, with `.` for the checkout's root, for example `feedbax:web`. A derived key always has the separator, so no page is ever given Mandible's own notes, even one served from the root of a Mandible checkout (`mandible:.`). The app of an embedding page is not something the page states: the daemon derives it from the page's origin (`src/interface-notes/embed-identity.ts`). It accepts only an http(s) origin on a loopback host (`localhost`, `*.localhost`, `127.x.x.x`, `[::1]`), finds the processes listening on its port (`lsof -iTCP:<port> -sTCP:LISTEN`), requires that it can read every listener's working directory and that they share one, takes that directory's checkout root and origin remote from git, and resolves them with `resolveProjectForCheckoutReadOnly`: a registered checkout root, or any checkout, a worktree or a clone, whose remote is a registered project's identity. Nothing is registered by this, and nothing is cached: the listener, its directory and the project are read on every request, so a port taken over by another server gets that server's name.

The derived name is a label, not authentication. A process chooses its working directory, so an `ssh -L` tunnel, a static file server or an agent started in a checkout is named after that checkout too; and `lsof` run as the owner lists only the owner's processes, so the name assumes every loopback listener belongs to the owner. Whether a page may use the name is the operator's decision.

**Grants.** The bridge gets an identity only for an app the operator has allowed. A grant is for an app of a project, `feedbax:web`: once allowed, a page whose listener runs in that app's directory of any checkout of the project (the main checkout or any worktree), on any loopback port and under any loopback name, gets the toolbar. A server of another project, or of another directory of the same project (`feedbax:.`, `feedbax:desktop`), asks on its own. `POST /api/interface-notes/embed-identity { origin }` answers `EmbedIdentity { app, project: { id, key, name } }` when the app its listener's directory names is allowed. Otherwise it records a pending request for that app in `interface_note_embed_grants`, one row per project and app, with the origin and directory of the page that asked, and answers 403 `origin_not_granted` with the request. The origin and directory on a row are where the latest page that asked (or, once allowed, the latest page served under the grant) came from; they are shown to the operator and are never part of the decision. A page cannot invent an app, since the app is read from its listener's directory, so a page asking under many `*.localhost` names updates one row; an unanswered request expires after seven days (`PENDING_GRANT_TTL_MS`). The identity route answers 400 `origin_not_loopback` and 404 `origin_not_registered` as above. The Settings view's Issues section lists the apps, pending first, as "project, path/" with the latest origin and directory, with Allow, and Revoke or Dismiss, through `GET`, `PUT { project, app }` and `DELETE ?project=&app=` on `/api/interface-notes/embed-grants`; the embed's link opens it with `section=settings-issues&embed_origin=<origin>`, which marks the row whose latest origin that is. Every note write the bridge makes names the page's origin (`embed_origin=<origin>`, `INTERFACE_NOTES_EMBED.originParam`), and the daemon reads the grant again for each one: the write is accepted only for notes of a granted app, and a new note must record that origin; otherwise it answers 403 `origin_not_granted`. So a Revoke takes effect on a page that is already open, while Mandible's own interface, which names no origin, still edits and removes those notes. Nothing is granted from the embedding page or the bridge: the bridge calls only the identity route and the note routes. All these routes require the operator and follow the notes' home, so a preview that keeps notes in its source asks the source. The grants are backed up with the other metadata. Migration 245 keyed the grants by app; of an app's earlier rows by origin and directory, a granted one was kept, else the latest request.

**A grant is a courtesy approval.** Allow is a click in Mandible's own top-level window, which web content cannot make: an embedding page can only ask, and cannot frame or script Mandible's pages (issue b30bc8c tracks closing same-site framing of them). It is not proof that the owner decided: any process running as the owner, agents included, can call the grant routes with the owner's local identity. Agents must never grant, allow, or revoke an embed grant; they direct the owner to Settings → Issues.

**Provenance.** A note made through the embed records its page's origin (`origin` on the note, migration 244), and its page URL must be on that origin: the bridge refuses a create whose `target.url` is elsewhere, and the daemon refuses a note whose origin is not a loopback origin, whose page URL is not on it, or which names an origin for Mandible's own app or none for another app. The comment body states it as the first line of the note's block, before the note's text: `Made on: <origin> (<app>), not in Mandible`, so no text the page wrote stands between that line and the start of the block. The ledger `source` of the issue, comment and revision stays `mandible`, since it names the subsystem that wrote the row, the daemon's notes store; the origin on the note and in the body is what tells an agent and the operator that the text arrived through a page rather than being typed in Mandible.

**Embed and bridge.** The daemon serves two paths outside the API: `/embed/notes.js`, the embed bundle, with `Access-Control-Allow-Origin: *`, and `/embed/bridge`, a page that loads the bridge bundle, with `Content-Security-Policy: frame-ancestors` listing the loopback origins (all ports, http and https) and `Referrer-Policy: no-referrer`. The browser boundary (`validateDaemonBrowserBoundary`) still refuses every other cross-site request; it admits these two only for their own `Sec-Fetch-Dest` (`script`, `iframe`), after the Host check, and skips the remaining checks for them because a cross-site load carries the page's Origin. A preview's gateway authorizes each request by asking the production instance's forward-auth route with the original request's headers and its method and URI in `X-Forwarded-Method` and `X-Forwarded-Uri`. For a GET or HEAD of one of the two documents, named by an absolute path in `X-Forwarded-Uri` (never resolved against a base, so `//x/embed/bridge` is not the bridge), that route lifts only the cross-site refusal; the request still passes the instance and Origin checks like any other. So the embed of a preview works only once the production instance runs a build with this rule.

The embed (`ui/src/annotation/embed.tsx`) runs only in a top window and mounts once. It adds the bridge as a hidden iframe on the daemon's origin (the origin it was loaded from) and says hello by `postMessage`. The bridge (`ui/src/annotation/bridge.ts`, `createBridge`) takes the parent's origin from that message, which the page cannot forge, asks the identity route for it, answers with the identity, or null with whether the request is pending, and from then on answers only that window and origin. Every note operation is then a message to the bridge (`bridgeProtocol.ts`), which calls the ordinary API as a same-origin page with the app, the page's origin and the project's id: lists, creates and edits for the granted app, filing onto a new issue of the granted project. The bridge creates only notes whose page URL is on the parent's origin, edits, deletes and files only notes it has listed or created for this page, and files onto an existing issue only when its own `has_notes` listing returned it, which it asks for by project id (`/api/issues?project=<id>`, matching no repo name, root or key); so a page can reach no other app's notes and no other project's issues. It forwards the app's `interface_note:changed` events. On a null identity or no answer within ten seconds the embed removes the frame and mounts nothing but, for a pending request, the link. The bridge's calls are authenticated as Mandible's own interface's are, on the daemon's origin (`client-auth-token.ts`), so they carry the operator's identity and the routes' ordinary checks apply.

**Accepted risks.** A granted app writes as the operator into its project: script injected into an allowed app's dev server (a dev server is not hardened against content from the open web) can file issues and comments there whose text reads as the operator's, marked only by the origin line. Removing that would need a human gesture on a daemon-origin page for each filing. A grant covers the app's server in every checkout of the project, so it extends to worktrees and branches made after the Allow, including a branch whose code the operator has not read, and to any port they are served on. Browser state on a port outlives the server on it: a service worker, cache entry or the embed's pending writes left on `http://localhost:3000` by one server run or replay when another server holds the port, under the second server's app if that app is allowed. So allow only apps of projects whose code you trust, and revoke an app when its checkouts may serve code you do not.

The embed renders the menu in an open shadow root of a `mandible-interface-notes` element, with the design tokens rebound from `:root` to `:host` and a `data-theme` from `prefers-color-scheme`; Agentation draws its own toolbar in a portal on the page's body, as on Mandible. The bundle (`ui/embed-build.mjs`) is self-contained, uses Preact for React, and is built with `process.env.NODE_ENV` set to `development`, because Agentation records a note's React components and source file only then. Agentation also records components only on a page it detects as React (`isReactPage`: a `__reactFiber$` or `__reactProps$` key on the body, the root element or a child of the body), which a React 18 or later `createRoot` app does not provide, so the host element carries a `__reactProps$mandibleInterfaceNotes` key.

### Alternatives considered

- For other apps, a proxy route on the daemon's local socket, with an `embed` route policy and an `x-mandible-embed` header, reached through each app's dev server. Each app would need server-side code and the socket path, the app would have been named by the request, and the daemon would have needed a third class of browser identity. The bridge needs one script tag and no new identity: its requests are ordinary same-origin requests, and the app is derived from facts of the machine rather than stated.
- For other apps, the derived identity alone, with no grant. The page would opt itself in by loading the script, and any listener in a checkout (a tunnel, a static server, a third-party project's dev server) would get the operator's voice in that project. The grant puts that decision with the operator, once per app of a project.
- For other apps, a confirmation on a Mandible page for each filing. It would remove the risk that script on an allowed page files in the operator's name, at the cost of leaving the app for every Send. Not chosen; the risk is stated above.
- For other apps, CORS on the notes routes for loopback origins. It would open the API itself to cross-site requests from any local page and require credentials on cross-origin fetches; the bridge keeps the API same-origin and limits what an embedding page can ask to the bridge's operations.

- Agentation's `endpoint` sync protocol instead of callbacks and a cache. The daemon would host the package's sessions, annotation CRUD, health poll and event stream, and would need a class of browser write routes without the `x-mandible-csrf` header. Its gain is animated removal of filed pins and no remount after filing; it has no path for pushing a loaded issue's notes into the toolbar, so the remount would remain for loading. Not chosen.
- Comments with an empty body and the notes rendered by every consumer. Each consumer of comment bodies (UI, CLI show and report, search, export, mirrors) would need the notes separately. The generated body gives all of them the one text form at no cost and keeps revision history on the existing path. Chosen.
- Notes owned by the issue body as well as by comments, so that a new issue's notes could be its description. The second owner type complicates every rule and conflicts with agents editing issue bodies. Comment-only ownership, empty body on a filing-created issue.
- For previews: CORS with an origin allowlist on the source for the notes routes (touches the browser security boundary, and the source would have to know live preview origins), or writing notes back when the launcher finalizes a preview (delayed until the preview ends, which may be days, and bypasses the source daemon). Forwarding over the local socket is used instead.
- Relying on the package's `autoClearAfterCopy` setting to clear filed pins. It is the user's setting, also affects Copy, and its clear is indistinguishable from the user's. The remount is used instead.

### Verification

Tests at the boundaries that can fail, in the gate: filing moves listed unfiled notes in one transaction, skips ones filed meanwhile, and regenerates the body; a text edit of a filed note produces a comment body revision; removing the last note soft-deletes the comment; a body edit of a carrying comment is refused; `has_notes` filtering and ordering; the migration converges. In the browser flow: a note survives clearing site data; a note older than seven days is shown; notes from two pages are filed together and their pins leave the toolbar; Show pins on an issue shows them on the right page, and Clear while loaded changes nothing on the issue; the Chat composer still renders and removes pills through the shared component. For other apps: the bridge's guards hold against crafted messages (`test/interface-notes-bridge.test.ts`); a page is named only after the operator allows its app, which then covers that app's server in another checkout on another port while another app on an allowed port asks, never as Mandible's own app, and not when a listener's directory is unreadable; a note's origin must match its app and page URL and is stated first in its filed block; the bridge's writes stop when the grant is revoked; pending requests expire; grants by origin and directory migrate to one per app; a note under one app is absent from another's list; filing for an app creates the issue in its project, where `has_notes` finds it; the identity route resolves a worktree to its project and refuses a non-loopback origin, an unregistered checkout and a port with listeners in different directories (`test/interface-notes-apps.test.ts`); the embed's two paths pass the browser boundary only cross-site as a script and as a frame, and a gateway's forward-auth request for them still passes the remaining checks (`test/server-write-boundary.test.ts`); a note made through the embed on a React `createRoot` page records its components (`test/provisioned/interface-notes-embed.test.ts`). No string or style snapshots.
