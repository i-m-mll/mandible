# Auth Queue API

The auth queue manages protected-branch merges and other authenticated actions. Agents submit requests; the user approves via the dashboard or terminal.

## Types

Auth request types: `merge`, `commit`, `force-push`, `branch-delete`, `config-change`, `data-delete`.

Auth request statuses: `pending`, `executing`, `approved`, `needs_rebase`, `completed` (exit 0), `failed` (non-zero exit, with `failure_reason`), `rejected`, `withdrawn`, `superseded`, `expired`, and legacy `dismissed`.

## Endpoints

### POST /api/auth/check

Check whether a merge request is clean against its target branch and queued
pairwise-independent merge requests. The check is read-only: it rejects tracked
dirty worktree state and in-progress merges before using Git merge-tree objects
without writing to the worktree.

**Request body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `cwd` | string | yes | Protected-branch worktree path used for Git checks |
| `base_branch` | string | yes | Target branch |
| `head_branch` | string | yes | Candidate branch |
| `repo` | string | no | Repository name used to filter queued requests |
| `request_id` | string | no | Existing request ID to exclude during revalidation |

**Response:** `200 OK`

```json
{
  "check": {
    "status": "clean",
    "repo": "myrepo",
    "base_branch": "main",
    "head_branch": "feature/foo",
    "checked_requests": 2,
    "conflicts": []
  }
}
```

### POST /api/auth/request

Submit a new auth request.

**Request body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `command` | string | yes | Shell command to execute on approval |
| `title` | string | yes | Dashboard display title |
| `type` | string | no | Auth request type (default: `merge`) |
| `session_id` | string | no | Submitting session ID |
| `cwd` | string | no | Working directory for command execution |
| `repo` | string | no | Repository name (auto-derived from `cwd` if missing) |
| `base_branch` | string | no | Target branch |
| `head_branch` | string | no | Source branch |
| `files_changed` | number | no | Number of files changed; computed server-side for merges |
| `additions` | number | no | Lines added; computed server-side for merges |
| `deletions` | number | no | Lines deleted; computed server-side for merges |
| `diff_summary` | string | no | Unified diff content; replaced by the server-captured diff for merges |
| `commit_message` | string | merge | Merge commit message (canonical change message when `canonical_message` is true) |
| `canonical_message` | boolean | merge | Must be true for a merge request. Declare `commit_message` as the agent-authored canonical change message; the daemon validates its envelope, canonicalizes it, and records `commit_message_digest` |
| `verification` | string | merge | Required with `canonical_message`. The machine-owned `Verification:` section text; the daemon rejects a message whose section does not match it |
| `post_merge_handoff` | string | no | Handoff note for next session |
| `protected_root_dirty_action` | object | no | Merge only. What an explicit protected-root dirty policy did: `{policy, action, branch, worktree, stash, files: [{status, path}], message}`. Stored on the request and returned read-only as `protected_root_dirty_action` |
| `issue_references` | string[] | no | Issue IDs to attach for context; not closed on merge |
| `issue_closures` | string[] | no | Issue IDs to close on successful merge |
| `issues` | string[] | no | Legacy close-on-merge issue IDs; prefer `issue_closures` |
| `depends_on_id` | string | no | Auth request ID that must complete first |
| `execution_mode` | string | no | `daemon` or `remote` |
| `supersedes_request_id` | string | no | Exact pending request to supersede atomically |
| `superseded_action_dispositions` | object[] | no | `{ordinal, reason}` for each staged predecessor action not carried identically |

Requests carry no spec. A body containing `spec_content` is refused with `400`;
state post-merge manual steps under the change message's `Caveats:` and link a
substantial design to the issue as an artifact. Requests submitted before this
rule keep their stored `spec_content`, which the detail route returns read-only.

**Response:** `201 Created`

```json
{ "request_id": "a1b2c3d4-...", "files_changed": 3, "additions": 24, "deletions": 8 }
```

Merge submission captures an immutable `change_report` from the exact reviewed
commits. The request detail exposes the shared `AuthChangeReport` contract,
including its per-file inventory, totals, classification versions and comparison
commit IDs. Caller-supplied counts and diff content cannot override this capture.
Prose edits preserve it; a replacement candidate captures a new report through
supersession. Historical requests without a captured report return `null`.
Collection errors or the 10,000-file limit reject submission explicitly.

**Error responses:**
- `400` — Invalid payload
- `409` — Duplicate request exists, or merge-tree independence check found a conflict
- `422` — Merge preflight could not run safely, such as tracked dirty state or merge-check infrastructure failure

```bash
curl -X POST http://localhost:19420/api/auth/request \
  -H 'Content-Type: application/json' \
  -d '{
    "command": "mandible auth merge feature/foo --into main",
    "title": "Merge feature/foo: add widget",
    "type": "merge",
    "cwd": "/path/to/repo",
    "repo": "myrepo",
    "base_branch": "main",
    "head_branch": "feature/foo",
    "issue_references": ["umbrella123"],
    "issue_closures": ["abc1234"]
  }'
```

### PUT /api/auth/request/:id

Revise a pending auth request. Terminal and executing requests are immutable; submit an explicit replacement for changed reviewed bytes.

**Request body:** Any supported mutable metadata subset from POST (except requester identity and supersession fields). `spec_content` is refused.

**Response:** `200 OK` with the updated request object.

**Error responses:**
- `400` — Validation error (descriptive message returned)
- `404` — Not found
- `409` — Invalid status transition
- `422` — Invalid command

```bash
curl -X PUT http://localhost:19420/api/auth/request/a1b2c3d4 \
  -H 'Content-Type: application/json' \
  -d '{"title": "Updated title", "diff_summary": "..."}'
```

### DELETE /api/auth/request/:id

Retired. Returns `410 Gone` without changing durable request or lifecycle records.

**Query params:**

| Param | Type | Description |
|---|---|---|
| `type` | string | Filter by auth request type |

**Response:** `200 OK`

      "type": "merge",
      "status": "pending",

### POST /api/auth/request/:id/approve

Approve a pending request after fresh configured-operator signing proof. The signed challenge binds the exact request/action snapshot, nonce, and 60-second validity. Failed, cancelled, expired, or drifted proof leaves the request pending. Success transitions to `executing`. Protected merges require local isolated candidate publication; unsupported native preparation hooks fail before effects; native post hooks use the frozen convergence plan.

**Response:** `202 Accepted`

```json
{ "request_id": "...", "status": "executing" }
```

### POST /api/auth/request/:id/cancel-proof

Cancel the configured operator's in-flight signing challenge. Requires `approve_auth`; unavailable through file RPC. Returns `200` with `{ "cancelled": true }`. It does not reject or withdraw the pending request, and cannot undo an already verified approval.

### Scoped protected-merge clearances

`GET /api/auth/clearances`, `GET /api/auth/clearances/:id`,
`POST /api/auth/clearances`, and `POST /api/auth/clearances/:id/revoke` are
operator-only. `POST /api/auth/request/:id/clearance/execute` is available only
to the exact active API-token credential recorded when that request was
submitted. Clearance execution is merge-only, daemon-only, runtime-bound, and
atomically consumes one use while freezing the reviewed request and recording
the clearance, signer lease, requester credential, and snapshot digest.

```json
{
  "request_id": "optional-auth-request-id",
  "grantee": "agent-user-or-slug",
  "grantee_credential_id": "credential-id",
  "project": "canonical-project-key",
  "base": "main",
  "action": "merge",
  "issue": "exact-issue-ref",
  "head": "feature/exact-head",
  "duration_minutes": 60,
  "max_uses": 1
}
```

### POST /api/auth/request/:id/withdraw

## Auth Hooks

Auth hooks are commands that run automatically after successful auth actions. They are configured per-repo and per-action-type.

Reading the hook registry is open. **Creating, updating, or deleting a hook
requires the `change_settings` global capability** — registering a hook
registers a command Mandible executes unsupervised after a protected merge, so
it is an authority change, not ordinary state. Unauthenticated mutations return
`401` in strict client-auth mode; an authenticated caller without the capability
returns `403`.

### GET /api/auth/hooks

List all auth hooks.

**Response:** `200 OK`

```json
{ "hooks": [{ "id": "...", "repo_pattern": "*", "auth_type": "merge", "command": "npm run build", "label": "Build", "enabled": true, "position": 0 }] }
```

### GET /api/auth/hooks/:id

Get a single hook.

**Response:** `200 OK` — hook object.

### POST /api/auth/hooks

Create a new hook.

**Request body:**

| Field | Type | Required | Description |
|---|---|---|---|
| `repo_pattern` | string | yes | Glob pattern for repo name (`*` for all) |
| `auth_type` | string | yes | Auth request type that triggers this hook |
| `command` | string | yes | Shell command to run |
| `label` | string | yes | Human-readable description |
| `enabled` | boolean | no | Whether the hook is active (default: true) |
| `position` | number | no | Execution order |
| `required` | boolean | no | Whether the hook is part of convergence (default: true). A failed required hook makes the request `merged / convergence failed` and withholds its deferred issue closures. |

**Response:** `201 Created` — hook object.

```bash
curl -X POST http://localhost:19420/api/auth/hooks \
  -H 'Content-Type: application/json' \
  -d '{"repo_pattern": "mandible", "auth_type": "merge", "command": "npm run build && npm start", "label": "Rebuild and restart"}'
```

### PUT /api/auth/hooks/:id

Update an existing hook. Accepts any subset of the creation fields. Requires
`change_settings`: an update can rewrite the command bytes of an already-trusted
hook, so it carries the same authority requirement as create.

**Response:** `200 OK` — updated hook object.

### DELETE /api/auth/hooks/:id

Delete a hook. Requires `change_settings`. Built-in hooks cannot be deleted (returns `403`).

**Response:** `200 OK`

```json
{ "deleted": true }
```

## Convergence

`status: "completed"` with `exit_code: 0` says the merge landed. It does not say
the machine is running the merged bytes. Every auth request projection
(`GET /api/auth/queue`, `GET /api/auth/history`, `GET /api/auth/request/:id`,
and the `auth:resolved` / `auth:merged` SSE payloads) carries a `convergence`
object:

```json
{
  "convergence": {
    "state": "failed",
    "hooks": [
      {
        "hook_id": "builtin-mandible-rebuild",
        "label": "Build Mandible after merge",
        "state": "failed",
        "required": true,
        "attempts": 3,
        "max_attempts": 3,
        "exit_code": 1,
        "command_digest": "…",
        "started_at": 1786933884126,
        "finished_at": 1786933899001
      }
    ]
  }
}
```

`state` is `none` (no hook registered), `complete`, `pending`, or `failed`.
A `pending` or `failed` state withholds the request's deferred issue closures
until convergence completes.

### POST /api/auth/request/:id/retry-convergence

Grant one more attempt to the failed hooks of a merged request and rerun them.
This reruns the snapshotted hook command only — it never reruns the merge, which
is why it needs no fresh merge authorization.

**Request body (optional):**

| Field | Type | Required | Description |
|---|---|---|---|
| `hook_id` | string | no | Retry only this hook. Omit to retry every failed hook. |

**Response:** `200 OK`

```json
{ "request_id": "…", "convergence": { "state": "complete", "hooks": [] } }
```

### Runtime self-update gates

A merge request whose repository matches the enabled `builtin-mandible-rebuild`
hook self-updates the running installation. Its merge check, submission and
approval refuse while the runtime handoff lock is held
(`docs/runtime-handoff.md`), and approval requires a passing candidate
acceptance of its exact current candidate (`docs/candidate-acceptance.md`).
Queue, detail and history payloads and `auth:updated` carry
`candidate_acceptance`: `{ state, reason, started_at, finished_at }`, where
`state` is `none`, `running`, `passed`, `failed` or `stale`. It is `null` when
acceptance does not apply.

#### POST /api/auth/request/:id/candidate-acceptance

Start acceptance of the current candidate unless a run of it is open or has
passed. Requires project write access.

**Response:** `202 Accepted` with `{ "request_id": "…", "acceptance": { "state": "running", … } }`

#### GET /api/auth/request/:id/candidate-acceptance

Return `{ "request_id": "…", "acceptance": … }` with the same shape.

#### GET /api/runtime-handoff/lock

Return `{ "lock": null }` or the held lock with its `journalPath`,
`bindingDigest`, `requestId`, `phase`, and `error`.

#### POST /api/runtime-handoff/retire

Operator only. Retire a held lock whose journal phase is `failed`.

| Field | Type | Required | Description |
|---|---|---|---|
| `binding_digest` | string | yes | The held lock's exact binding digest. |
| `reason` | string | yes | Why the failed handoff is retired. |

### Convergence alerts

A required hook that exhausts its attempts raises exactly one inbox alert per
(request, hook) pair, surfaced as `hook_alerts` in `GET /api/inbox` and
`GET /api/inbox/global`. Acknowledge one with
`POST /api/inbox/hook_alert/:id/ack`. Acknowledging dismisses the notice only —
the durable hook row still reads `failed` until a retry actually succeeds.
